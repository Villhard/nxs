# Хранение записей и подключение tracker

Без настройки tracker используются `.scratch/<feature-slug>/spec.md` и `.scratch/<feature-slug>/issues/<NN>-<slug>.md`. Спека задачи хранит намерение; проектная SPEC - реализованное. Для обычной работы не требуется предварительная настройка или секция `## nxs`.

## Подключение другого tracker

Чтобы использовать другой tracker, подготовь Markdown-инструкцию о его реальном хранилище spec и tickets и доступных операциях. В ней опиши, как читать записи целиком, включая body, comments, зависимости и статусы; создавать и обновлять spec и tickets; работать с зависимостями и статусами; проверять фактический результат операций. Можно попросить агента подготовить такую инструкцию обычной просьбой.

Добавь необязательный pointer в уже применимые project instructions, в секцию `## nxs`:

```markdown
## nxs
Трекер: docs/tracker.md
```

Pointer также может находиться в применимых global instructions; project pointer имеет приоритет над global. Относительный путь разрешается от файла instructions, содержащего pointer, а `~` - от домашнего каталога пользователя. Загрузка instructions находится вне ответственности skills. Pointer не предоставляет доступ к tracker и не устанавливает инструменты: нужные доступы и операции должны быть доступны отдельно.

Явный путь или URL обозначает конкретную запись и сам по себе не переключает backend: необходимо установить принадлежность записи и использовать соответствующую согласованную инструкцию, при неоднозначности - уточнить. Если настроенная инструкция отсутствует или недоступна либо недоступна необходимая операция, затронутая работа останавливается с причиной, без fallback в `.scratch` или создания второго набора записей. После неизвестного результата записи сначала прочитай ее фактический эффект и IDs, прежде чем повторять операцию.

Явный вызов `to-spec` или `to-tickets` с согласованным remote назначением разрешает соответствующую публикацию; вызов `dev-exec` для remote ticket - необходимые обновления этого ticket в согласованном проекте. Другие файлы не публикуются, parent не закрывается и копии не синхронизируются без запроса.

## Необязательный профиль Backlog.md

[Профиль Backlog.md](../trackers/backlog.md) - самостоятельная tracker instruction для отдельного локального backlog проекта. После явного подключения новые task specs хранятся в Backlog.md docs, а tickets - в задачах со ссылками на эти документы. Проектные `SPEC.md`/`.SPEC.md` остаются на своих местах, диагнозы и evidence `rnd-debug` - локально. Не переноси секреты и частные инструкции в backlog. Чтение README или установка nxs ничего не настраивает и не мигрирует.

### Подготовка Backlog.md

Подготовка хранилища - отдельное действие человека по [разделу профиля](../trackers/backlog.md#подготовка-человеком); агент не выполняет setup автоматически. Раздел входит в сам профиль и доступен после копирования без checkout nxs.

Скопируй [профиль](../trackers/backlog.md) в `docs/tracker.md` своего проекта, затем добавь в применимые project instructions pointer из примера выше. Например, из корня проекта, если исходный checkout уже доступен:

```bash
mkdir -p docs
cp -n /path/to/nxs/trackers/backlog.md docs/tracker.md
```

Если файл уже занят, выбери другой свободный путь и укажи его в pointer, не перезаписывая чужую инструкцию. Профиль можно скопировать и без checkout; установленным skills не нужны checkout nxs или другой skill. Дальнейшие операции и остановки описаны в самой копии профиля.

Профиль проверен с Backlog.md `1.53.0`, Codex CLI `0.166.0` и реальным TUI на disposable fixtures, включая отдельные source-вызовы `to-spec`, `to-tickets`, `dev-exec`. Точный охват и ограничения - в [профиле](../trackers/backlog.md#проверенная-область); это не заявление native регистрации или совместимости всех клиентов и версий. Справочные источники: [CLI](https://github.com/MrLesk/Backlog.md/blob/v1.53.0/CLI-INSTRUCTIONS.md) и [конфигурация](https://github.com/MrLesk/Backlog.md/blob/v1.53.0/ADVANCED-CONFIG.md).
