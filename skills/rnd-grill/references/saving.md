# ПРЯМОЕ СОХРАНЕНИЕ

Читай при запросе на сохранение и входе из трекера. Сохранение необязательно и выполняется внутри `rnd-grill`, без цепочки decision/spec/ticket и журнала.

## ИСТОЧНИК И МЕСТО

Сначала прочитай явно переданный локальный файл; отсутствие/ошибка чтения останавливает затронутую работу. Ключ/URL трекера прочитай доступным интерфейсом, иначе попроси текст. Не угадывай содержимое по ключу. Установи источник, применимые родительские решения/комментарии или доказанное отсутствие таковых и блокеры. Метка готовности и отсутствие поля блокеров не доказывают готовность. Неизвестные предпосылки запрещают передачу как готового, но не явно согласованный черновик. Укажи проверенные предпосылки и нужные результаты: идентификаторы и статусы их не доказывают.

Предпочитай явное или установленное место. Решение в `research/` функции относится к ней, не к вложенной новой функции. Несколько задач, путей или владельцев требуют выбора; ветка не устанавливает владельца. Для новых локальных записей используй `.scratch/<feature-slug>/`: короткий lowercase slug через дефис, возможно с префиксом ключа трекера. Не ищи посторонние настройки хранения, не запускай setup и не публикуй/синхронизируй записи.

До предложения правок прочитай источники и существующие цели. Сохрани применимые решения, условия, defaults, ответы, исключения, причины, требования проверок, замечания и вопросы. Внешние источники не меняй; смена оформления не разрешает потерю содержания. Карты и типизированные решения - контекст, не implementation tickets и не разрешение конвертации. Используй их идентичность без изменения истории ради нового результата.

## ПРЕДЛОЖЕНИЕ И ОДОБРЕНИЕ

Покажи точное содержимое, путь, состояние (согласовано или незавершено/черновик) и пределы готовности. Для существующего результата покажи правку, не генерируй заново. Разделяй факты, допущения, предложения, принятые выводы, замечания и вопросы. Явно запрошенное незавершенное состояние может хранить вопросы; согласие сохранить не отвечает на них.

Каждая запись требует согласия на ее содержание, путь и охват. Просьба сохранить разрешает подготовку, не непоказанные выводы. Используй точное подходящее согласие либо спроси и жди. Глоссарий показывай отдельным предложением по [доменным правилам](domain-modeling.md); одно одобрение не покрывает другое. Доменному запросу не нужны обертка решения и каталог функции. При отказе файлы не меняй. Одобрение HTML не запрашивает сохранение и не одобряет непоказанные Markdown или доменные правки.

## ФОРМЫ РЕЗУЛЬТАТА

Выбирай полезную запись, не по одной каждого вида. В старых документах принимай прежние английские заголовки шаблонов как соответствующие русским; не переписывай историю только ради языка:

- Решение: по умолчанию `research/decision.md`, [шаблон](../assets/decision.md). Сохрани согласованное/незавершенное состояние, охват, выводы и причины, предложения/варианты, доказательства, замечания/вопросы и следующий разрешенный шаг. При согласованной замене вывода сохрани прежние причины.
- Описание функции: по умолчанию `spec.md`, [шаблон](../assets/spec.md). Семь допустимых `##` заголовков сохраняй по порядку; "Проблема" и "Решение" обязательны, остальные можно опустить лишь пустыми. В "Решение" - поведение, условия, значения по умолчанию, учтенные ответы и приемочные проверки; в "Решения по реализации" - факты, интерфейсы, ограничения и ссылки на проектные записи; в "Решения по проверке" - требования проверок; в "Вне задачи" - исключения. Источник, охват согласия, замечания и `[NEEDS CLARIFICATION: <вопрос>]`, не относящиеся к другой секции, - в "Дополнительные заметки". Черновое состояние укажи в этих секциях. Локальный lowercase `spec.md` - не проектный `SPEC.md`/`.SPEC.md` и не доказательство реализации.
- Исследование, обзор или дизайн: короткий отчет в `research/`, например `<topic-slug>.md`, `architecture-audit.md`, `<module-slug>-design.md`. Включи нужное из [методов](evidence-methods.md), без обязательного отдельного решения/описания функции.
- Опросник: по умолчанию `research/questionnaire-<recipient-slug>.md`, [правила](questionnaire.md) и [шаблон](../assets/questionnaire.md). Сохрани идентификаторы, точные вопросы, полные/частичные ответы, авторство и блокеры. Подготовка и одобрение не разрешают отправку, контакт или выдуманные ответы.
- Доменные записи: только одобренные термины по правилам/формату проекта. Постоянные правила построенной работы записывает только `dev-spec` в проектные спецификации.

При необходимости скопируй совместимый разрешенный исходный feature spec без изменений либо адаптируй, сохраняя применимое содержание. Не дублируй существующий локальный spec ради пути по умолчанию. Укажи пути/URL, нужные версии или переданные снимки; чтение источника не равно наблюдению. Точный hash используй только по пользе/запросу для изменяемого источника, поясни объект; hash не означает согласия. При побайтовом копировании/повторном использовании контекст передай в ответе, не меняй файл ради метаданных.

## ЗАПИСЬ И ОТВЕТ

Перед записью перепроверь источник и цель. Согласуй конкурентные изменения и непокрытые правки; устаревшее предложение не разрешает затереть работу другого. Идентичный результат ничего не меняет. Сохрани ручные дополнения, ссылки, прежние доказательства и историю; широкое разрешение сохранить не разрешает удаление. Не включай секреты, частные настройки и сырые диалоги в документы или внешние сервисы.

Запиши лишь одобренное, перечитай файлы и проверь состояние, источники, требования, приемочные проверки, вопросы и сохранность. Сообщи пути, правки/повторы без изменений, отклоненные записи и точные ограничения. Event IDs, approval hashes, locks и файлы состояния запуска не нужны.

Достаточный согласованный объем можно передать в отдельно разрешенный `dev-exec` с описанием функции или без него. Передай источник, одобренный охват, намерение, реальные предпосылки, доказательства и вопросы. Неизвестная/невыполненная предпосылка не дает назвать работу готовой; проверь результат, не статус. Сохранение не создает tickets, не реализует исправление, не меняет Git/настройки/установки и не запускает следующий скилл.
