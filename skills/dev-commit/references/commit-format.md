# КОММИТ: ФОРМАТ И STAGING

1. Установи разрешенный scope; без него выдели атомарные группы только своей работы. Прочитай `git status`, staged и unstaged diff, а также необходимые untracked файлы целиком. Пустой охват - no-op. Не включай чужое, секреты или изменения с неясным владельцем.
2. Формат сообщения определяют явные пользовательские и применимые проектные правила, включая настройку `Коммиты` в `## nxs`. Иначе используй одну короткую lowercase строку `<type>(<scope>): <subject>`, где type - `feat`, `fix`, `refactor`, `chore` или `docs`; не добавляй trailers без запроса.
3. До изменения index выбери случай для каждой группы:
   - Index пуст или содержит только эту группу: stage точные пути или разделимые hunks, просмотри весь staged diff и сделай обычный commit.
   - Есть чужой staged, а выбранные пути целиком содержат только эту группу: новый untracked файл сначала точечно stage; просмотри будущий diff выбранных путей и используй `git commit --only -m "<сообщение>" -- <paths>`. Это берет рабочие байты целиком, не частично staged версию.
   - Есть чужой staged и выбранный путь смешивает группы либо владение неясно: остановись до записи index и запроси разделение или уточнение. Никогда не применяй whole-file `--only` к mixed-пути.
4. Не используй stash, reset, alternate index или временную перезапись файлов для обхода; не меняй рабочие файлы. Не делай push, force, amend или `--no-verify` без отдельного разрешения. Ошибка проверки, staging или commit останавливает операцию; hook не обходи. При неизвестном результате сначала сверь HEAD и index, не повторяй вслепую.
5. Сообщи созданные commit IDs и оставшиеся изменения, отдельно чужие. Не заявляй сохранность, которую не проверил.
