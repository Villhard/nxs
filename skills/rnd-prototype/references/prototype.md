# PROTOTYPE

## LOCATION AND PRESERVATION

Use an explicitly supplied feature directory, or choose `.scratch/<topic-slug>/` with a short lowercase hyphenated slug. If the candidate directory contains `map.md`, choose a different slug unless the user explicitly authorizes work there. Create a distinct `research/prototypes/<experiment-slug>/` directory for the temporary experiment and save `research/<experiment-slug>-verdict.md` alongside it. Inspect destinations first; do not overwrite existing work. Link the verdict to the actual retained files. Follow project preferences for local uncommitted prototypes. Do not stage, commit, transfer, reuse or delete them without separate authorization; never treat them as production scaffolding.

## CHECK AND VERDICT

Make the experiment clearly temporary and easy to run. Choose a representative, bounded input and an observable expected outcome before executing the check. Use isolated data and avoid product writes or external effects. A visual or preference question requires the user's judgment; a runnable demonstration alone does not establish that judgment. If relevant access, tools or evidence are missing, record the limitation instead of claiming a pass or failure.

The verdict names the question and hypothesis, why the check is relevant, setup and exact steps, inputs, observed results, status (supported, rejected or inconclusive), assumptions and limits. A failed hypothesis is a valid result. An inconclusive result names the missing evidence or next discriminating check. Distinguish an observed result from an expected result or interpretation. Do not include secrets, private configuration or raw session transcripts in artifacts.
