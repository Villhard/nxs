# ВЫБОР И ИСПОЛЬЗОВАНИЕ ТРЕКЕРА

- Найди необязательную строку `Трекер: <путь к Markdown-инструкции>` в применимых project instructions (`## nxs`), затем в global instructions. Project важнее global; без обеих используй локальный default `.scratch/<feature-slug>/spec.md` и `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, без setup. Путь разрешай относительно содержащего instruction file; `~` - домашний каталог пользователя.
- Явный путь или URL во входе обозначает конкретную запись, а не молчаливое переключение backend. Установи ее принадлежность и используй соответствующую согласованную инструкцию; при неоднозначности уточни. Если явно настроенный документ отсутствует/не читается или инструмент недоступен, останови затронутую операцию с точной причиной, без fallback и второго набора записей.
- Прочитай инструкцию и фактические записи, включая body, comments, dependencies и статусы. Следуй ее операциям и соответствиям; не выдумывай команды, возможности или credentials. Локальные поля и значения tickets определяет bundled контракт ticket у соответствующего skill.
- Явный вызов `to-spec`/`to-tickets` с согласованным remote назначением разрешает соответствующую публикацию; вызов `dev-exec` для remote ticket - необходимые обновления этого ticket в согласованном проекте. Не публикуй другие файлы, не закрывай parent и не синхронизируй копии без запроса. После неизвестного результата записи сначала прочитай фактический эффект и IDs, не создавай дубликат.
- Сохраняй пользовательскую историю, ручные дополнения и ограничения; не раскрывай секреты. Диагностический отчет `rnd-debug` остается локальным evidence и автоматически не публикуется.
