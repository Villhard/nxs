# FEATURE SOURCE

Read before consuming input or choosing a feature spec destination. These rules belong to to-spec; `rnd-debug` applies its own feature-directory reference and gates.

## SOURCE AND LOCATION

Read an explicit local file first. A missing or unreadable source stops; never reinterpret its path as a fresh request. A saved decision, including an unfinished one, supplies context rather than approval of its proposals. An existing feature spec can be reused in place; an external source remains unchanged.

Resolve an explicit destination or established feature/artifact location before choosing a default. A decision under a feature's research directory belongs to that feature, not a new nested feature. Ask when multiple destinations remain plausible. For new work use `.scratch/<feature-slug>/spec.md`, with two to four lowercase English words joined by hyphens; a tracker key prefixes the slug when applicable. Keep Markdown local under `.scratch/` without consulting tracker-backend preferences, running setup or publishing remote records.

A map directory holds decision work: use a distinct feature unless explicit implementation scope names that existing directory. Keep map files and decision tickets, including bare or Markdown-bold `Type:` files, byte-identical. Existing paths take precedence over defaults but do not grant revision or implementation permission.

Inspect an existing target before any copy. Reuse an identical spec unchanged; a different result requires approval of its concrete revision. Copy a compatible authorized external spec unchanged, or adapt its layout to the bundled template while retaining applicable content and source identity. Source answers, conditions, exclusions and testing requirements survive layout changes.

Record a local source's path and SHA256 of its actual bytes. For a clear request identify the supplied request and its approved scope; hash the exact supplied text and identify what was hashed, rather than inventing a source file. For read/pasted external content retain its original identity and hash of the exact supplied/read content, naming any supplied snapshot. On byte-identical reuse or copy, record source pins in the journal and handoff without altering the spec. Never treat a document's existence, ready label or hash as approval.

## REMOTE INPUT

Read a tracker key or URL through an available read interface; otherwise request pasted content and stop until it is available. Establish source identity, applicable parent decisions/comments (or evidence that no parent applies) and blocker state. A key, ready label or omitted blocker field does not establish content or dependency-free readiness. State missing evidence explicitly.

A known open remote blocker requires a verified mapping to a local ticket in the target feature. Preserve that dependency and inspect the local result needed by the proposed handoff in the working tree; a resolved status alone is insufficient. Never equate remote and local issue numbers or synchronize their statuses. Verified closed remote blockers remain satisfied context with their supporting evidence. Unknown or unmapped blockers prevent a ready handoff. An authorized draft may retain the specific missing parent/blocker evidence as clarification; it never fills it with an invented answer.

## PROJECT CONTEXT

Read affected glossary entries and ADRs where project instructions place them, typically GLOSSARY.md or GLOSSARY-MAP.md and docs/adr/. Use recorded terms and decisions; absence is normal and requires no question. Read project specs under the bundled reader contract. These files and all source decision histories are evidence, not outputs of this skill.
