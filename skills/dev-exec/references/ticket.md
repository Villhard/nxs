# КОНТРАКТ TICKET

Владелец контракта - `to-tickets`; исполнитель `dev-exec` использует такую же bundled копию. Новый ticket содержит заголовок, `**What to build:**`, `**Blocked by:**`, необязательный `**Branch:**`, `**Status:**`, checkboxes приемки, `## Условия завершения` и `## Комментарии`. Укажи цель, существенные решения и ограничения, требования проверки и ссылки на source spec/диагноз/выбранные finding IDs так, чтобы новая сессия не зависела только от общего каталога. Старые заголовки и историю не мигрируй ради формы.

- `**Blocked by:**` - конкретные идентификаторы и ссылки на настоящие blockers; `None (can start immediately)` только при их отсутствии, не при неизвестности. Для remote предпочитай native blocking links, иначе явно запиши ссылочные blockers. `resolved` сам по себе не доказывает наличие нужного результата.
- `**Branch:**` - только согласованная ветка, если она нужна; без поля исполнитель работает на текущей ветке.
- `**Status:**` - `ready-for-agent` для согласованной работы с известными предпосылками; `needs-info` для разрешенного черновика с изолированным `[NEEDS CLARIFICATION: <вопрос>]`; `ready-for-human` при необходимом действии человека; `resolved` после всей приемки и обязательных проверок; `wontfix` по решению пользователя или явному исключению. Существенные противоречия источника не превращай в ready ticket. Для remote используй настроенные соответствия без создания labels без запроса.
- Checkboxes описывают наблюдаемые критерии, отмечаются после проверки. В `## Комментарии` сохраняются результаты, решения и история; у существующего ticket используй существующий раздел комментариев.
- Новые локальные номера идут после максимального существующего, blockers прежде зависимых. Существующие IDs, статусы, критерии, история и `Do not commit` сохраняются; `resolved`/`wontfix` не переоткрываются автоматически.
