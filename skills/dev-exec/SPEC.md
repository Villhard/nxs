# dev-exec

## Purpose

Execute an entrusted implementation ticket or clear request in the current session through inspection, an approved plan and verification. A clear request needs no invented ticket, feature spec or mandatory interview; review, built-work project specs and commit remain separate operations.

## Ownership

Own the current-session execution context and approval boundary. Consume unchanged ticket rules/template owned by `to-tickets`, project-spec reader rules owned by `dev-rnd` and journal/controlled-run resources owned by `dev-lead`; bundle them so independent installation needs no other installed skill. The checker enforces shared-copy agreement and explicit invocation policies.

## Boundaries

Explicit invocation or an explicit controlled scope permits inspection and planning. Implementation writes require approval of the concrete plan and stay within the entrusted task, applicable ticket execution fields and journal records. Preserve unrelated working/index changes and ticket history. Never stage, commit, push, write project specs or start review/spec/commit implicitly; installation changes need explicit authorization. Native permissions remain effective.

## Contracts

- Resolve task identity from explicit input or established context, never a branch alone. Missing or unreadable ticket input stops instead of becoming a clear request. Preserve decision-map histories and bare or bold `Type:` decision files, including `Type: task`, without implementing them. Remote input requires source, decision and dependency evidence; unknown or unmapped blockers stop affected execution and local execution changes no remote state.
- Show a concrete plan and wait for human approval in standalone use, reusing approval only for the covered plan and scope. A complete controlled packet instead requires a saved, hashed plan and `needs_input` before implementation, followed by recorded lead approval and continuation of the same native session. A journal, ready ticket, feature approval or saved plan alone grants no implementation approval. Reconcile changed inputs and return substantial plan changes for approval; scope, external-contract and settled-decision changes return through lead to the user.
- Apply ticket status, blocker-status and material-clarification gates before implementation. Select the ticket branch before inspecting and checking actual prerequisite results; status, names and ancestry alone prove no result. A missing, reverted or unverifiable result gets Comments and a journal entry, then a stop without asking, merging, cherry-picking or implementing the blocker. A carried or squashed result may pass by current-tree evidence.
- An undone or unverifiable required environment action follows the human-step round trip with expected evidence; after the human resets the ticket, verify the result without repeating the action. A clear request records the pending action without creating a ticket. Only a complete controlled context with an approved feature plan naming the action and exact target authorizes performing it; missing authorization or unverifiable results remain blockers, and native permissions still apply.
- Verify every applicable criterion and required project check before resolving a ticket; retain incomplete work and actual limitations. Preserve review-origin non-reproduction/wontfix exceptions only where the ticket grants them. Record meaningful decisions, checks and handoffs in the journal and applicable ticket Comments. A clear request reports its checked result without ticket status. Controlled completion remains a proposal for independent lead acceptance.

## Known limitations

Built-in Plan Mode is optional. Approval instructions establish no technical write prohibition and permit no bypass of native mode restrictions, including journal-write limits. Source inspection and packaging checks establish neither live execution, native registration/delivery nor permission enforcement. Candidate ticket/clear-request behavior and Plan Mode remain unverified in Codex, Claude Code and OpenCode; implementation-worker execution and continuation are not candidate behavior evidence. Existing `/plan` defaults, producers, coordinator routes and user installations remain unchanged; no route-switch gate has passed.
