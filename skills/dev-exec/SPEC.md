# dev-exec

## Purpose

Execute an entrusted implementation ticket or clear request in the current session through inspection, an approved plan, verification and authorized commit checkpoints. A clear request needs no invented ticket, feature spec or mandatory interview; review and built-work project specs remain separate operations.

## Ownership

Own the current-session execution context and approval boundary. Consume ticket rules/template owned by `to-tickets`, project-spec reader rules owned by `dev-spec` and journal/controlled-run resources owned by `nxs-lead`; bundle them so independent installation needs no other installed skill. The checker enforces shared-copy agreement and explicit invocation policies.

## Boundaries

Explicit invocation or an explicit controlled scope permits inspection and planning. Implementation writes require approval of the concrete plan and stay within the entrusted task, applicable ticket execution fields and journal records. Preserve unrelated working/index changes and ticket history. Commit checkpoints require user approval covering their explicit scope and native permissions; push, PR and installation changes need separate authorization. Never write project specs or start review/spec implicitly.

## Contracts

- Resolve task identity from explicit input or established context, never a branch alone. Missing or unreadable ticket input stops instead of becoming a clear request. Preserve decision-map histories and bare or bold `Type:` decision files, including `Type: task`, without implementing them. Remote input requires source, decision and dependency evidence; unknown or unmapped blockers stop affected execution and local execution changes no remote state.
- Show a concrete plan and wait for human approval in standalone use, reusing approval only for the covered plan and scope. A complete controlled packet instead requires a saved, hashed plan and `needs_input` before implementation, followed by recorded lead approval. Resume the same native session where the host documents continuation; otherwise reconcile prior effects and start a new bounded run with the approved answer, saved plan and artifacts, plan hash, recorded approval and original boundaries. Verify approval against the current plan in either case; unresolved effects stop the affected action without automatic replay. A journal, ready ticket, feature approval or saved plan alone grants no implementation approval. Reconcile changed inputs and return substantial plan changes for approval; scope, external-contract and settled-decision changes return through lead to the user.
- Define separately checkable logical blocks and, by default, propose a checkpoint with an explicit commit scope for each committable block. Combine changes that cannot be safely separated; plan without checkpoints when the user intentionally selects no commits or an existing ticket prohibits them. In standalone and controlled execution, after the necessary checks pass, apply `dev-commit` in the same session and verify the result before the next block. Lead independently verifies controlled results. Missing authorization, permission or skill availability stops the affected checkpoint; failed checks, unsafe separation or uncertain commit effects do not establish one. Reconcile uncertainty without automatic replay. Existing ticket `Do not commit` prohibitions remain binding unless a specific revision is separately approved; execute those tickets without checkpoints. If commits are not selected, hand off uncommitted changes. Review follows the ticket, and a commit alone does not complete or accept it.
- Apply ticket status, blocker-status and material-clarification gates before implementation. Select the ticket branch before inspecting and checking actual prerequisite results; status, names and ancestry alone prove no result. A missing, reverted or unverifiable result gets Comments and a journal entry, then a stop without asking, merging, cherry-picking or implementing the blocker. A carried or squashed result may pass by current-tree evidence.
- An undone or unverifiable required environment action follows the human-step round trip with expected evidence; after the human resets the ticket, verify the result without repeating the action. A clear request records the pending action without creating a ticket. Only a complete controlled context with an approved feature plan naming the action and exact target authorizes performing it; missing authorization or unverifiable results remain blockers, and native permissions still apply.
- Verify every applicable criterion and required project check before resolving a ticket; retain incomplete work and actual limitations. Preserve review-origin non-reproduction/wontfix exceptions only where the ticket grants them. Record meaningful decisions, checks and handoffs in the journal and applicable ticket Comments. A clear request reports its checked result without ticket status. Controlled completion remains a proposal for independent lead acceptance.

## Known limitations

Built-in Plan Mode is optional. Approval instructions establish no technical write prohibition and permit no bypass of native mode restrictions, including journal-write limits. Separate Codex fixture observations do not establish an end-to-end route, native registration or permission enforcement. Clear-request behavior, Plan Mode and other clients remain unverified. Existing `/plan` tickets and user installations are not migrated by source removal.
