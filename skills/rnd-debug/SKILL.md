# /rnd-debug

Исследуй сбой и сохрани доказательства. Запускай только по явному вызову или прямо разрешающей инструкции. До входа прочитай [правила каталога](references/feature-directory.md), для доменных доказательств - [проектных спецификаций](references/project-specs.md), для источника в трекере - [правила трекера](references/tracker.md). Сначала прочитай переданный источник и комментарии; отсутствие/ошибка чтения останавливает затронутую работу. Используй согласования лишь в их пределах. Feature spec и ticket не нужны; существующие записи не дают нового разрешения.

## ИССЛЕДОВАНИЕ

Построй самый дешевый цикл проверки симптома, воспроизведи и сократи шаги/данные. Ранжируй проверяемые гипотезы с разными предсказаниями. Меняй один параметр/пробу за раз; проследи подтверждаемое объяснение через обоснованные "почему" до устранимой причины. До объявления причины подтверди симптом и различающую гипотезы пробу. Запиши минимальное обоснованное направление исправления и дешевую устойчивую регрессионную проверку на ближайшей практичной публичной границе. Разделяй наблюдения, правила источников, ожидания и допущения.

Используй чтение и ограниченные одноразовые пробы, без инструментирования и правок продуктового кода/тестов. Нужные временные файлы и результаты держи в `research/` функции вдали от production data. Удаляй лишь одноразовые файлы проб, чья очистка разрешена диагностикой; сохраняй чужую работу и полезные доказательства, сообщай реальную очистку. Установка, миграция и внешнее действие требуют согласия на действие/цель плюс native permissions; иначе останови эту пробу, назови ожидаемый результат и недостающие доказательства. После прерывания проверь эффекты перед повтором сомнительного действия.

Если сбой не воспроизводится, доказательства недоступны или подходят несколько причин, сохрани попытки, ранжированные гипотезы, точный пробел и следующую различающую пробу. Причина - unconfirmed, направление исправления и регрессионный тест - pending. Не предлагай готовое исправление или передачу на реализацию.

Подтвержденную причину сопоставь с применимыми проектными спецификациями и релевантной документацией:

| Класс | Доказательство | Дальше |
| --- | --- | --- |
| `right` | Намерение записано, код ему противоречит | Предложи подготовить исправление через `to-spec` при необходимости и `to-tickets`. |
| `silent` | Намерение не установлено записями | Согласуй намерение, затем предложи подготовку через `to-spec`/`to-tickets`. |
| `wrong` | Запись описывает устаревшее/ошибочное поведение | Согласуй исправление, предложи `to-spec`/`to-tickets`; project spec меняет только `sync-spec` после реализации. |
| `feature` | Текущее поведение было выбрано, запрос меняет решение | Предложи `rnd-grill`, не готовое исправление. |

Спрашивай класс лишь при нескольких обоснованных вариантах. Для `wrong`/`feature` укажи путь записи, для `silent`/`wrong` - доказательство согласия.

## ДОКУМЕНТ И ПОВТОР

Сохрани `.scratch/<feature-slug>/root-cause.md` по правилам места. Секции: `## Симптом`, `## Воспроизведение`, `## Доказательства`, `## Гипотезы`, `## Пять почему`, `## Причина`, `## Направление исправления`, `## Регрессионная проверка`. В старом диагнозе принимай прежние соответствия: Symptom, Repro, Evidence, Hypotheses, 5-Why, Root cause, Fix direction, Regression test; не переписывай его лишь ради языка. Явно укажи confirmed/unconfirmed и класс, точные шаги, предсказания, результаты проб, пути доказательств, очистку и допущения. Для `feature` - необходимость смены решения и ожидание регрессии до него.

До записи прочитай диагноз и относящиеся доступные tickets с этой причиной. Если открытый ticket уже покрывает ту же подтвержденную причину, оба файла оставь и сообщи повторное использование/новые доказательства в диалоге. Для другой причины при открытом ticket покажи правку диагноза и конфликт, получи выбор этой правки или другого места. Не меняй tickets: сохрани идентичность, ограничения ветки, `Do not commit`, статус и историю; resolved/wontfix не меняй. В одобренной правке сохрани ручные дополнения и прежние доказательства; идентичный результат ничего не меняет. Не меняй implementation tickets, доменные/проектные спецификации, продуктовый код/тесты, Git/index, настройки и установки. Диагностика не создает ticket и не исправляет продукт.

## РЕЗУЛЬТАТ

Верни документ, подтвержденность, класс намерения, источники, согласования, реальные пробы и оставшиеся предпосылки. Для подтвержденного `right` или `silent`/`wrong` с нужным согласием предложи передать диагноз в `to-tickets`, при необходимости сначала сохранить согласованное исправление через `to-spec`. Не создавай ready ticket сам; подтверждение причины не доказывает предпосылки и не разрешает исправление. Для unconfirmed назови недостающие доказательства, для `feature` предложи `rnd-grill`. Последующий `sync-spec` записывает существенные изменения проектных спецификаций после исправления кода. Следующий skill сам не запускай; remote публикацию диагноза не выполняй.
