# КАТАЛОГ ФУНКЦИИ

Читай до входных документов и записи артефактов функции. Применяй подходящие секции; условия и результат `rnd-debug` остаются его собственными.

## МЕСТО

Предпочитай явный/установленный каталог. Для новой диагностики используй `.scratch/<feature-slug>/`: два-четыре английских lowercase слова из запроса через дефис; ключ трекера ставь впереди: `.scratch/<KEY>-<slug>/`. Источник в `research/` функции относится к ней, не к вложенному новому каталогу. Несколько задач, мест или владельцев требуют вопроса; ветка не устанавливает задачу.

Осмотри место до записи. Сохрани существующие данные и чужие правки. При неясном охвате или владении уточни цель до записи.

## ЛОКАЛЬНОЕ ХРАНЕНИЕ

Новый диагностический Markdown по умолчанию идет в `.scratch/`; явно переданный существующий локальный документ обновляй на месте. Создавай лишь диагноз и полезные доказательства проб, без предварительных feature specs и tickets. Настройка трекера определяет чтение источника по [правилам](tracker.md), но диагноз остается локальным evidence. Не меняй настройки, не запускай setup, не публикуй/синхронизируй remote issues. Исключи секреты, частные настройки и сырые диалоги.

## ВХОД ИЗ ТРЕКЕРА

Ключ/URL разрешай и читай вместе с комментариями через выбранный по [правилам](tracker.md) backend. Явная ссылка выбирает запись, не переключает backend молча. Недоступная настройка или инструмент останавливают затронутое чтение; не угадывай по ключу и не переходи в локальное хранилище.

Установи источник, применимые родительские решения/комментарии или их отсутствие и блокеры по интерфейсу/переданному тексту. Недостающее спроси: ключ, метка готовности и отсутствие поля блокеров не доказывают отсутствие препятствий. Сохрани известные предпосылки и нужные результаты; существующие локальные tickets - с их идентичностями и проверенным соответствием. Не создавай ticket ради диагноза. Remote issue number - не локальный номер; remote label не разрешает закрыть local ticket. Неизвестная/невыполненная предпосылка блокирует заявление о готовности: проверяй реальный результат, не статус. Независимая безопасная диагностика может продолжаться в разрешенных пределах. Закрытые проверенные блокеры запиши с доказательствами.

## СОХРАННОСТЬ ИСТОЧНИКА

Существующие `spec.md`, решение и внешний источник читай как доказательства, не копируй и не переписывай. Перенеси в диагноз применимые намерение, условия, ответы, исключения, требования проверок и ссылки. Для `root-cause.md` не нужен промежуточный spec. Подготовительную спецификацию сохраняет `to-spec`, tickets - `to-tickets`, реализованные проектные спецификации - `sync-spec`.

Проверь открытые вопросы и в источнике, и локально. Одобрение spec не закрывает вопрос; согласованное решение открывают только новые противоречащие доказательства.

## ДОМЕННЫЕ ДОКУМЕНТЫ

Прочитай относящиеся к задаче записи глоссария, если они есть: обычно корневые `GLOSSARY.md`/`GLOSSARY-MAP.md` или пути из инструкций. Используй канонические термины, не запрещенные синонимы. Отсутствие нормально, не спрашивай. Не создавай и не меняй эти файлы.

Проектные спецификации тоже доменные документы; читай по [правилам](project-specs.md).
