# /nxs-setup

Проверь конкретную настройку, project instructions или shared global configuration. В рамках запроса согласуй чтение project specs, ветки, реальные команды проверок, необязательный трекер и формат коммитов. Покажи один точный diff, запиши лишь одобренное и остановись. Это отдельная помощь, не стадия разработки.

Вход: `project`, `global` или конкретная цель; `project --readiness`/`global --readiness` дают только отчет. Пример: `/nxs-setup project`. Следующий шаг предлагай, не запускай.

Сначала обработай `--readiness`: только с явным режимом, по [правилам готовности](references/readiness.md); сообщи и остановись. Пропусти обычный аудит, вопросы/предложения пакета, записи и проверки после них. Для обычной настройки действуют правила ниже.

## ОБЩИЕ ПРАВИЛА

Режим задает допустимые файлы, свою секцию, вопросы и источники аудита.

- До одобрения показанного diff не пиши. Применяй точно его; запрошенную пользователем поправку сначала покажи заново. При отказе ничего не пиши и сообщи неизменность всех файлов.
- Своя секция: от ее заголовка до следующего `#`/`##` либо конца файла. Несколько ее заголовков в проверяемых файлах останавливают: назови файлы/строки для ручного объединения.
- Повтор меняет секцию на месте, показывает лишь разницу; пользовательская правка внутри возвращается к проверенной строке. Вне затронутых секций сохраняй каждый byte, включая final newline.
- Личные правила держи снаружи секции. Эквивалент снаружи считай покрытием с цитатой строки. Если при одобрении меняют строку внутри, объясни, что повтор снова предложит проверенную, и предложи вынести личное правило наружу.
- Нет предложения - сообщи "уже настроено", без diff, остановись.
- После записи выполни проверки режима, исправь сбои до отчета.
- Недостающее сообщай, не выдумывай команды, правила и скиллы.
- До применения сверь source/target: устаревший diff не затирает конкурентное. Покажи/согласуй непокрытые правки. Сохрани посторонние bytes, symlinks/settings; секреты/частные настройки не копируй в shared files.
- Не устанавливай, не обновляй и не удаляй скиллы, не добавляй hooks, не мигрируй задачи и не переписывай личную конфигурацию из-за смены source contracts. Нужную provenance сообщай отдельно; source/wiring не доказывают native registration/совместимость.

## РЕЖИМ

| Вход | Действие |
| --- | --- |
| `project --readiness`/`global --readiness` | Только отчет готовности, затем стоп. |
| `project` | Шаги ниже. |
| `global` | [Глобальная настройка](references/global.md) и [карта возможностей](references/capabilities.md). |
| Конкретная цель | Секция "Конкретная цель". |
| Без аргумента | Спроси проект или конкретную цель. |
| Неподдержанный вход | Спроси конкретный охват и остановись. |

## КОНКРЕТНАЯ ЦЕЛЬ

Для названной инструкции, документа или настройки изучи цель и связанные источники. Спрашивай лишь существенный недостающий охват/полномочия. Для agent instructions прочитай [правила написания](references/writing-for-agents.md). Покажи один полный пакет точных diffs, путей и настроек с последствиями для приватности; получи одобрение. Узкая цель не подразумевает project/global setup. Сохрани посторонние bytes/symlinks/settings, не переноси частное в shared. Отказ ничего не пишет, актуальное не требует предложения. Примени точно одобренное и проверь.

## ГРАНИЦЫ ПРОЕКТНОГО РЕЖИМА

Дальнейшие шаги относятся к `project`. Для инструкций читай [правила написания](references/writing-for-agents.md).

- Только целевой instruction file, новый `CLAUDE.md` с `@AGENTS.md`, одна ignore-строка `.scratch/` и согласованная Markdown-инструкция трекера по названному пути. Не код, другие instructions, пользовательские tickets, index/коммиты.
- Своя секция - одна `## nxs`; необязательны строки `Трекер` и `Коммиты`. Правила извне учитывай покрытыми с источником; project settings важнее global.
- Уточняй только необходимые выборы, включая место и операции трекера, затем получи одобрение точного diff.

## АУДИТ

Из корня сначала читай, затем предлагай. Для каждого пункта запиши найденное с путем либо отсутствие.

1. Перечисли корень (`ls -a`), найди точные `AGENTS.md`/`CLAUDE.md`, разреши `realpath`. Одинаковый realpath считай одним файлом/одним набором `## nxs`. Цель выбирай по первой строке:

   | Найдено | Цель |
   | --- | --- |
   | Ровно одна `## nxs` среди реальных файлов | Ее реальный файл. |
   | Больше одной | Стоп по общим правилам с файлами/строками. |
   | Оба имени ведут в один файл | Реальная цель symlink. |
   | `CLAUDE.md` содержит строку `@AGENTS.md` | `AGENTS.md`. |
   | Только `AGENTS.md` | Он. |
   | Только `CLAUDE.md` | Он. |
   | Оба независимы | `AGENTS.md`; при одобрении назови `CLAUDE.md` альтернативой. |
   | Ни одного | Новый `AGENTS.md` и `CLAUDE.md` с `@AGENTS.md`. |

   Меняй target, не symlink. Рядом с существующим не создавай второй instruction file.

2. Прочитай `## nxs` в границах общих правил.
3. Найди правило веток в instructions/`CONTRIBUTING.md`; перечисли ветки `git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`. Явное правило вне секции считай покрытым с цитатой; строка "Ветки:" ссылается на файл вместо повтора. Без правила при большинстве веток единого другого формата предложи его как вывод по именам. Иначе `<type>/<short-description>`, type = `feat`, `fix`, `refactor`, `chore`, `docs`.
4. Найди test suite, linter, type checker. Прочитай все существующие источники по порядку:

   | Источник | Команды |
   | --- | --- |
   | `Makefile`, `justfile` | Соответствующие targets/recipes (`test`, `lint`, `typecheck`, `check` и аналоги): `make <target>`, `just <recipe>`. |
   | `package.json` | Соответствующие scripts с package manager по lock file. |
   | CI (`.github/workflows/*.yml`, `.gitlab-ci.yml`, другие корневые CI) | Реально выполняемые команды. |
   | `pyproject.toml` | Tool config pytest/ruff/mypy/pyright и подобное; способ запуска из lock/CI, например `uv run pytest`. |

   Предлагай первую подходящую команду по порядку; расхождения перечисляй. Wrapper target одной утилиты - одна команда. Назначение без команды отсутствует, строку секции убери.
5. Выполни `git check-ignore -q .scratch/`: 0 - уже ignored, без предложения; 1 - не ignored; прочий exit останавливает с ошибкой.
6. Прочитай [правила трекера](references/tracker.md), существующие project/global pointers и названные ими инструкции. Без выбора другой настройки работает локальный `.scratch` без setup; не добавляй pointer ради самого pointer. Если пользователь хочет настройку, project default для новой инструкции - `.scratch/nxs/issue-tracker.md`, global default - `~/.agents/docs/issue-tracker.md`. Сохрани существующую инструкцию и records; изменения только по согласованному diff.
7. Для иного backend изучи доступные CLI/MCP/API tools, help/docs и существующие настройки, согласуй проект/место и реальные операции. Read-only проверь доступ. Инструкция должна содержать `## Хранилище`, `## Чтение`, `## Запись`, `## Зависимости и статусы`, `## Проверка`: реальные пути/проект и интерфейс, чтение body/comments, создание и обновление spec/ticket, зависимости, результаты и соответствия статусов. Для remote предпочитай native blocking links, иначе явно записывай ссылочные blockers. Не выдумывай команды, capability или secrets; непроверенные операции пометь непроверенными. Пробная запись допустима только в явно разрешенную тестовую цель. Нет доступа - назови причину и не объявляй backend рабочим, не меняй рабочую конфигурацию на догадку.
8. Найди явный формат коммитов и ограничения в project instructions/`CONTRIBUTING.md`. При запросе настройки предложи необязательную строку `Коммиты: <формат сообщений и ограничения проекта>` с найденными или согласованными правилами; не подменяй их default форматом и не создавай коммит.

## ПРЕДЛОЖЕНИЕ

Одним сообщением покажи аудит (найдено с источником/нет), полный unified diff всех записей и один вопрос одобрения:

- Секция `## nxs` по [шаблону](assets/project-section.md): в конце после пустой строки или замена существующей на месте.
- Если instructions нет - новые `AGENTS.md` с секцией и `CLAUDE.md` с `@AGENTS.md`.
- Если `.scratch/` не ignored - строка в `.git/info/exclude` (частно для клона, рекомендуется); альтернатива `.gitignore` для всех клонов.
- Если настройка трекера запрошена - точный diff названной инструкции и строки `Трекер`; локальный пример - [шаблон](assets/issue-tracker.md). При необходимости отдельно включи согласованную строку `Коммиты`.
- Вопрос: одобрить, выбрать `.gitignore`/другой целевой файл, изменить строки либо отказать.

Актуальная секция и ignored `.scratch/` не требуют предложения; отсутствие tracker pointer само по себе не недостаток.

## ЗАПИСЬ

После одобрения запиши instructions и только согласованную инструкцию трекера. Ignore line: путь `"$(git rev-parse --path-format=absolute --git-common-dir)/info/exclude"`, каталог создай при необходимости; `.scratch/` отдельной строкой с предварительным newline, если его нет. То же для `.gitignore`.

## ПРОВЕРКА

- Ровно одна `## nxs`; diff до/после затрагивает только эту секцию.
- Новый `CLAUDE.md` содержит `@AGENTS.md`.
- При одобренном ignore `git check-ignore -q .scratch/` = 0.
- При изменении tracker instruction сверь путь, содержимое и доступные read-only операции с одобренным пакетом; непроверенные write-операции назови явно, тестовые записи без отдельного разрешения не делай.

## РЕЗУЛЬТАТ

Назови измененные файлы либо "ничего не записано", недостающее и место ignore line. При tracked-правке предложи `/dev-commit`.
