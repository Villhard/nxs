# CONFIRMED ROOT CAUSE INPUT

Read the root-cause artifact and verify its minimized repro, discriminating probe, supported cause, class, fix direction and regression check. Unconfirmed causes, competing live hypotheses, missing evidence or a `feature` class produce no ready fix ticket. For `silent` or `wrong`, require evidence of user agreement on the intended behavior or correction. A project spec is context for later `dev-spec`, never a fix-ticket edit.

Read all existing issues and identify tickets naming this cause. An open ticket for the same cause is reused unchanged; preserve the root-cause file. An open ticket for a new cause requires a concrete user decision to revise it or close it before changing either artifact. A revision preserves identity, status, branch and execution history. Resolved and wontfix tickets remain unchanged; append new authorized work with the next number.

Propose one fix ticket in the same feature's `issues/`, naming the cause path, corrected behavior, minimized repro and regression check. Name a wrong glossary or decision record to correct, or the spec as context for `dev-spec` after the fix. Use the ticket rules for numbering, dependencies, fix branch and complete execution block. Save only after authorization covering the proposed content and destination.
