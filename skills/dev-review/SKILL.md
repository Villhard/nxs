# /dev-review

Проверь итоговую работу, объясни подтвержденные замечания и верни выбранные пользователем исправления. Задача может включать checkpoint, staged, unstaged, untracked и не иметь tickets. `git add` не нужен. Пример: `/dev-review`.

Следующий шаг предлагай, не запускай. Согласие используй лишь в его пределах; verdict/выбор замечаний не разрешает реализацию.

## ГРАНИЦЫ

Пиши только отчет review: не код, tickets, project specs, index, Git objects и коммиты. Проверка чужого PR обычна и не должна трогать ветку. Артефакты и статусы - контекст, не разрешение исполнения.

Используй чтение, для Git - `GIT_OPTIONAL_LOCKS=0`. Проверки могут создавать одноразовые caches/build output вне репозитория, но не менять рабочее дерево/Git; передай ограничение каждому агенту. Без auto-fix и snapshot updates. Агенты возвращают замечания, не пишут отчет и другие файлы.

## ОХВАТ

До выбора охвата прочитай [выбранный снимок](references/selected-snapshot.md): baseline, checkpoint, источники и актуальность. Закрепи охват до записи отчета и запуска агентов.

Контекст/ticket/каталог задают требования, не автоматическую выборку кода. Обычно проверяется вся итоговая задача, не случайный staged. Явное сужение (коммит, staged, файлы) сохрани, запиши исключения и не называй полной проверкой. Неясный запрос уточни; неизвестный флаг/слово не считай режимом, flags выбора охвата не добавляй.

Неясные владение/baseline или пропущенная обязательная работа останавливают. Не stage/stash/switch, не создавай tree и не переписывай чужое ради охвата. Пустой index не означает пустую работу: учти выбранные unstaged/untracked. Только при полном учете и пустом итоговом изменении можно завершить без нового отчета, объяснив намеренную отмену.

## ТРЕБОВАНИЯ

Используй цель пользователя, одобренный план и явно применимые описание функции, диагноз, tickets/review. Малой задаче каталог/ticket не нужен. Для переданной функции установи требования по контексту/с пользователем; статус не доказывает охват/поведение. Прочитай What to build и приемку применимых tickets, Problem Statement/Solution соседнего feature record (или их русские заголовки). Идентичности, историю и запреты сохрани, артефакты не мигрируй.

Каждый файл читай из выбранного снимка с точной версией. Отдельно переданное текущее требование можно читать с disk SHA256 даже в историческом review, явно обозначив это. Не заменяй index/commit версию диском молча. Статус/ветку читай из той же версии.

Явную цель сохрани; без нее возьми цель из требований, без обоих - `no stated goal`. Не выводи намерение/владение из commit subjects, ветки и diff. В отчете сохрани точное предложение цели и источник полномочий. Существенно недостающие требования останавливают до запуска, не заменяются выдуманной приемкой.

## СУЩЕСТВУЮЩИЙ ОТЧЕТ

Выбери место по секции "Документ" до записи. Прочитай [правила отчета](references/review-report.md), проверь существующий отчет и его актуальность.

| Состояние | Действие |
| --- | --- |
| Актуальный и полный | Спроси до повторной проверки, если свежий повтор еще не запрошен явно. |
| Незавершенный | Новый проход с заново установленным охватом; follow-ups сохрани как историю. |
| Устаревший/неверный | Новый проход; старые поля не исполняй и не считай доказательствами. |

До перезаписи сохрани открытые follow-ups с источниками. Вызов review не разрешает перезапись актуального отчета сам по себе; просьба проверить заново разрешает.

## ЗАПУСК АГЕНТОВ

До изменения отчета для агентного прохода прочитай [запуск](references/agent-launch.md) и проверь возможности для каждой роли. Каждый запуск - выбранным native subagent tool с полным пакетом. До агентов/прямого прохода прочитай [замечания](references/findings.md): "Уровни серьезности" применяются ко всем и собственным проверкам, "Проверка замечания" определяет каждый verdict.

До запуска/прямого прохода запиши "Охват", "Требования" и `sweep: incomplete` по формату отчета с перенесенными follow-ups. Пока идет новый проход, старый complete не должен оставаться.

Запусти три finder roles, параллельно при наличии мест:

- `review-quality`: ошибки, крайние случаи, обработка сбоев, гонки, ожидаемая нагрузка и базовая безопасность;
- `review-testing`: покрытие и качество тестов;
- `review-simplification`: добавленная сложность, повторное использование и неверный уровень исправления.

Четвертый, `review-verify`, запускается после всех finders. Для тривиального diff (dotfiles, только docs/форматирование) допустим прямой проход без агентов по тому же стандарту: сам найди кандидатов и дай verdict по правилам проверки. Один проход, без повторной перепроверки.

Дождись всех запущенных агентов и заверши before/after state checks до проверки кандидатов, новых запусков и записей. Неполная/неуспешная проверка останавливает проход; сохрани изменения, сообщи пределы без reset.

## СОБСТВЕННЫЕ ПРОВЕРКИ

Сам проверь требования, документацию и соглашения по тому же стандарту. До заявления "нет/не подключено" ищи: регистрация бывает вне diff, вызов - таблицей маршрутов/строкой.

- Требования: сопоставь поведение и всю приемку (`- [ ]` и `- [x]`) с итоговой работой и кодом вокруг. Проверь регистрацию/маршруты/настройки, критичные stub/TODO, незапрошенные правки, зависимости, публичный контракт и миграции. При узком охвате нетронутое требование само не замечание: его может покрывать другая работа. При `no stated goal` проверяй лишь подключение/полноту и скажи об этом.
- Документация: README, `docs/`, диаграммы/подписи/accessibility, CHANGELOG, `--help`, `CLAUDE.md`/`AGENTS.md`, глоссарий. Для переименованной команды/маршрута ищи старое и новое имя и вне diff; отличай устаревшее описание от верной истории/legacy use. Измененные и неизмененные документы читай/ищи в выбранном снимке с нужными unstaged/untracked, не из tip/index вместо них и не с исключенным чужим. Замечание - что diff сделал неверным или должен был добавить: flag, endpoint, option, зависимость, поведение/соглашение, устаревший термин, противоречие решению. Понятие, которого глоссарий никогда не покрывал, не замечание. Противоречие требованию - замечание.
- Проектные спецификации: читай по [правилам](references/project-specs.md) точных имен в выбранном снимке, не постороннем disk. Явно применимый private `.SPEC.md` закрепляй disk bytes. Противоречащая spec измененная строка - замечание с цитатой и путем. Отсутствующий spec, непокрытый модуль, новое пока незаписанное поведение (работа `/dev-spec`) и `(unconfirmed)` не замечания. Не замечание и согласованная замена конкретного утверждения: требование называет новое поведение и diff ему соответствует. Запиши в дальнейшие действия `pending dev-spec`, источник требования/точную инструкцию пользователя и заменяемую цитату с путем, также если verifier отклонил кандидата по этой причине. Исключение только для этого утверждения: голый путь spec, другое противоречие, несовпадающий с заменой diff и дефект кода рядом остаются замечаниями.
- Соглашения: прочитай применимые корневые и родительские `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`. Учитывай область at/below. Замечание - явное нарушение правила измененной строкой, с цитатой, путем и строкой; не вкус и не "дух документа". Правило, ставшее неверным из-за diff, - замечание документации.

Свои кандидаты тоже передай verifier.

## ПРОВЕРКА КАНДИДАТОВ

Finders и собственные проверки предлагают; verifier решает. По правилам замечаний объедини дубли, выходящее за охват перенеси в дальнейшие действия. Каждому оставшемуся дай id и передай всех, включая своих, одному свежему `review-verify` с полным пакетом. Не сообщай, кто выдвинул кандидата. Дождись результата.

Применяй вердикты как даны; сам не подтверждай, не опровергай и не удаляй кандидата.

| Verdict | Действие |
| --- | --- |
| `confirmed` | Оставь с серьезностью по доказательствам. |
| `plausible` | Оставь, не выше major, с нужным подтверждением. |
| `refuted` | Перенеси в отклоненные с доказательством verifier. |
| Нет verdict/не закончил | Проход incomplete; это не опровержение. |

`Noticed:` идет в дальнейшие действия как `not verified`. Сортируй оставшееся по серьезности, при равной confirmed раньше plausible, нумеруй с 1. Прямой проход применяет таблицу к собственным verdict.

Сохрани место, проблему, verdict и доказательства каждого, включая причины отклонения. Отклонение большинства нормально. Старый сломанный тест/линтер сообщай как остальное, не исключай из-за возраста.

## ДОКУМЕНТ

Пиши `.scratch/<feature-slug>/review.md`, если одна существующая функция однозначно определяется явным контекстом; ticket в `.scratch/reviews/` ее не задает. Не создавай каталог функции ради отчета. Несколько кандидатов требуют выбора. Без функции - `.scratch/reviews/<branch-slug>/review.md`; slug безопасный для ФС, при detached - `detached-<tip>`. Проверь, что путь внутри репозитория, включая symlinks. Если место само проверяется или занято другим, согласуй безопасный repository-local путь либо остановись.

Последний проход заменяет отчет, сохраняя открытые follow-ups с исходным запуском и `not re-verified`. Не теряй их при смене охвата. Старые ссылки tickets - история, не просьба создать/править/выполнять их.

После verifier заново установи снимок, baseline, checkpoint coverage, репозиторий, ветку, HEAD, index digest, цель и pins требований/контекста по актуальности отчета. Замечания запиши в любом случае, но complete - лишь при совпадении всего, успешных обязательных state comparisons и завершенных reviewers. Иначе оставь incomplete и причину. После hard kill уже записан incomplete. При внезапном изменении отчета не затри чужое; сообщи пределы, сохранив правки.

## КРАТКИЙ ОТВЕТ

Пиши коротко и понятно читателю без знания кода; термин объясни при первом употреблении.

1. "Что меняется:" - два-три предложения.
2. "Критичные", "Серьезные", "Небольшие" (пустые группы пропускай), номера как в отчете. У каждого жирное название с местом и по одному-двум предложениям: **Что это**, **Проблема** (вход/ситуация и неверный результат), **Исправление** (минимальное), **Если оставить** (эффект на пользователей/данные). Для plausible добавь `(plausible)` в название и **Что подтвердит**.
3. "Вердикт: можно выпускать." или "Вердикт: сначала исправить 1 и 3." Plausible учитывай как confirmed. Узкий verdict ограничь охватом; incomplete не получает разрешение выпуска. Auth/payment/crypto/migration требуют ручного security review сверх прохода, не разрешения выпуска.
4. "Отклонено: N".
5. "Не проверено:" - важные недоступные проверки и явные исключения одной строкой. Выбранные unstaged/untracked не исключены автоматически.
6. Путь отчета.

Без замечаний "Все хорошо. Можно выпускать." допустимо лишь для complete всей задачи без security limitation. Иначе назови границу/ограничение/неполноту. Всегда дай число отклоненных, пределы и путь. Если оставшихся замечаний нет, исправления не предлагай.

## ВЫБРАННЫЕ ИСПРАВЛЕНИЯ

Используй номера этого отчета. Явный прежний выбор сохрани, иначе спроси номера, `all` или `none`. Неясные/неизвестные номера и существенные варианты исправления уточни. Refuted и непроверенный follow-up - не проверенные замечания. Не создавай tickets, selection files, копии отчета и не меняй tickets.

До передачи проверь актуальность и complete. Устаревший/неполный/замененный отчет останавливает передачу до разрешения доказательств/выбора; номера другого прохода не используй.

В ответе передай путь и SHA256 отчета, выбранные номера, цель, scope/head/base/tip, snapshot pins, verdicts, доказательства, оставшиеся подтверждения, согласованные/открытые варианты. Невыбранное остается в отчете. `none` завершает без передачи исправлений. Это вход `dev-exec`, не новый протокол/разрешение его запустить.

## ОСТАНОВКА И ДАЛЬШЕ

Внеохватное - в дальнейшие действия. Неясные охват, владелец, baseline, существенные требования останавливают до запуска. Неполная проверка/ошибка state check оставляет incomplete. Чужое сохрани, без reset/clean/перезаписи.

Предложи `dev-exec` прямо с отчетом и номерами, без обязательного ticket. Он должен получить согласие на исправление/план, проверить текущие предпосылки и воспроизвести либо иначе подтвердить каждое замечание до правок; plausible требует названного подтверждения. Невоспроизведенное сохрани с результатом/доказательствами как unconfirmed, не исправляй. Подтвержденному нужны точечная проверка и по возможности regression test. Существенные вопросы и предпосылки остаются блокерами.

Не запускай реализацию сам. Выбор, verdict и отчет не разрешают реализацию, commit/push/MR/PR. Прежнюю явную многооперационную инструкцию используй только в ее одобренных пределах.
