# /dev-review

По явному вызову проверь работу и верни замечания. Не меняй код, тесты, tickets, project specs, index, Git objects или ветку; не исправляй автоматически и не запускай другие skills. Читай [project specs](references/project-specs.md). Переданный локальный ticket/spec и явно переданный внешний источник прочитай целиком вместе с комментариями; внешний источник используй только для чтения как доказательство. Если указанный источник отсутствует или недоступен либо передан только ID без локального пути или доступного источника, останови затронутую проверку и запроси конкретный источник или локальный путь; не угадывай и не создавай замену.

## ОХВАТ И ТРЕБОВАНИЯ

Вход - ticket, spec или согласованный контекст и необязательные Git baseline/охват. Сначала установи по источнику выбранный результат: один ticket либо вся фича/общая интеграционная работа. Имя ветки этого не определяет.

- Явно переданный ref имеет приоритет, но проверь, что он покрывает все выбранные commits и изменения.
- Для одного ticket без явного ref используй доказанный исходный HEAD его исполнения до первой продуктовой правки либо другой явно согласованный покрывающий scope. Соседние результаты в общей интеграционной базе не входят в review ticket автоматически. После доработки сохраняй охват исходного результата вместе с исправлениями, не сужай его до HEAD последнего исполнения.
- Для всей фичи используй доказанную общую границу всех выбранных результатов, не execution HEAD последнего ticket. Merge-base согласованной конечной целевой ветки с HEAD допустим только при однозначно подтвержденных происхождении и покрытии всей выбранной работы. В прямом режиме общий охват целевой ветки доказывай составом commits/изменений и явными исключениями, не присваивай фиче всю дельту ветки.

Сверь границу с исходными HEAD, commits и фактическими изменениями выбранных результатов. Имя ветки, статус `resolved` и одно ancestry не доказывают принадлежность или полноту. Если baseline не покрывает выбранные commits либо происхождение/общая граница неоднозначны, объясни неизвестное и запроси точный scope до запуска reviewers. Закрепи baseline OID, HEAD и выбранные пути/версии; явное сужение сохрани и сообщи исключения.

Для обычной итоговой работы собери общий снимок:

- `git diff --no-ext-diff --no-textconv <base-OID> --` - итог committed, staged и unstaged до рабочего дерева;
- отдельно staged и unstaged diff, включая index-only расхождения и взаимные отмены;
- `git ls-files -z --others --exclude-standard` и содержимое выбранных относящихся untracked файлов.

Для явно выбранного commit или staged-only scope читай содержимое соответствующей версии, не подменяй его рабочим файлом. Отделяй чужие изменения по доказательствам, не перемещая их. Непустой index сам по себе не сужает review. Используй чтение Git с `GIT_OPTIONAL_LOCKS=0`.

Найди применимые инструкции проекта и `CONTRIBUTING`, включая правила родительских каталогов, и прочитай переданный ticket, conversation или spec с критериями. Отсутствие стандартов сообщи явно, не придумывай их. Если spec нет, спроси источник; если пользователь подтверждает его отсутствие, отметь Spec как skipped, не pass. Учитывай применимые project specs: согласованное новое поведение, которому они еще не соответствуют, пометь `pending sync-spec` с источником решения, не объявляй нарушением старого решения.

## ДВА НЕЗАВИСИМЫХ REVIEWER

Запусти параллельно ровно двух независимых native subagents одним и тем же закрепленным набором изменений, требований, версий и ограничений. Передай каждому содержимое всех выбранных committed/staged/unstaged/untracked изменений и нужный контекст, либо точные способы прочитать закрепленные версии. Запрети правки кода, файлов, index и ветки и auto-fix. Где доступны ограничения host read-only, включи их; иначе честно сообщи, что запрет обеспечен только инструкцией. Не запускай вложенный клиент или заменяющий самостоятельный проход.

- **Standards:** найди существенные нарушения конкретных применимых стандартов. Для каждого приведи путь и цитату правила, место изменения и последствие. Не сообщай вкусовые улучшения, каталог smells или дубли того, что уже гарантирует formatter/linter.
- **Spec:** проверь полноту и правильность требований, регрессии затронутого контракта и выход за scope. Сверь код вокруг diff, крайние случаи и тесты. Для каждого замечания укажи требование, место, конкретный вход/ситуацию и последствие; не выводи дефект из одного названия.

Если подтверждено отсутствие spec, Spec reviewer получает тот же набор с явной отметкой отсутствия требований и возвращает skipped, не выдумывая их. Если native subagents недоступны, один не запустился или не завершился, результат incomplete; не подменяй его single-agent fallback и не объявляй pass. Дождись обоих. Отделяй неподтвержденные гипотезы от доказанных дефектов.

## РЕЗУЛЬТАТ

Перед финальным ответом сверь HEAD, выбранный diff и выбранные новые файлы с началом; изменение охвата делает результат incomplete. Не восстанавливай чужие правки и не fingerprint все дерево или ignored caches.

По умолчанию отчет только в разговоре: `## Standards`, `## Spec`; внутри каждой оси сортируй доказанные замечания по серьезности `critical`, `major`, `minor`, указывай место, доказательство и последствия. Для пустой оси укажи результат, для skipped/incomplete - причину и ограничения. Назови baseline, HEAD, охват, исключения, ограничения и pending sync-spec. Не объединяй оси общим рейтингом и не утверждай полноту при незавершенной проверке.

Только по явному запросу сохрани отчет: в заданный локальный файл либо, при известной feature, `.scratch/<feature>/review.md`. Если существующее содержимое конфликтует, разреши конфликт до записи; без известного места не создавай каталог. Выбранные исправления предложи передать в `to-spec`/`to-tickets`; сам tickets не создавай и следующий skill не запускай.
