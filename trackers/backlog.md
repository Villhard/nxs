# ПРОФИЛЬ BACKLOG.MD ДЛЯ NXS

## НАЗНАЧЕНИЕ И ГРАНИЦЫ

Это самостоятельная tracker instruction для локального Backlog.md одного проекта. Используй ее только при явном выборе через `Трекер: <путь к Markdown-инструкции>` либо для явно указанной записи, принадлежность которой этому tracker установлена. Project pointer в `## nxs` важнее global; относительный путь разрешается от файла с pointer, `~` - от домашнего каталога. Явный ID, путь или URL обозначает конкретную запись, а не разрешает молча сменить backend. При неоднозначной принадлежности уточни ее. Pointer не устанавливает инструмент, не дает доступа и не вызывает skills.

Без pointer действуют оба прежних default: `.scratch/<feature-slug>/spec.md` и `.scratch/<feature-slug>/issues/<NN>-<slug>.md`. При выбранном Backlog.md новые task specs храни в его docs, tickets - в tasks; не создавай их зеркала в `.scratch/`. Project `SPEC.md`/`.SPEC.md` остаются отдельными документами реализованных контрактов, диагнозы и evidence `rnd-debug` - локальными материалами, не зеркалом tracker. Родительская задача вместо task spec не нужна.

Команды соответствуют Backlog.md `1.53.0` и [документации этой версии](https://github.com/MrLesk/Backlog.md/blob/v1.53.0/CLI-INSTRUCTIONS.md). Фактически проверенная область и ограничения перечислены в конце; не переноси ее автоматически на другой клиент, версию или хранилище.

## ПОДГОТОВКА ЧЕЛОВЕКОМ

Этот раздел предназначен человеку для отдельной явно разрешенной подготовки. Агент не выполняет setup автоматически; pointer и установка skills не разрешают установку инструмента, init или миграцию.

Для подготовки нужен отдельно доступный Backlog.md; CLI рекомендуется для агентов, человеку достаточно TUI, MCP и Web UI не обязательны. Установка инструмента - отдельное решение пользователя.

Пример для Backlog.md 1.53.0: только в корне нового или одноразового проекта, изменения которого явно разрешены, и только если там и в родительских каталогах нет существующего backlog. Сначала сохрани чужие файлы и убедись, что выбранные `backlog/`, `.backlog/` и `backlog.config.yml` не заняты. Затем:

```bash
env -u BACKLOG_CWD backlog init "My Project" \
  --defaults --no-git --integration-mode none \
  --check-branches false --include-remote false \
  --bypass-git-hooks false --auto-open-browser false \
  --backlog-dir backlog --config-location folder
```

Init создает `backlog/` и `backlog/config.yml`. Флаги выбирают filesystem-only без Git-интеграции tracker и без клиентских инструкций; обычный init может записывать инструкции и выполнять Git-действия. Не добавляй к `--integration-mode none` флаги `--agent-instructions` или `--install-claude-agent`: версия 1.53.0 не принимает это сочетание. Не включай tracker auto-commit, bypass hooks, remote operations или callbacks смены статуса, в том числе на отдельных задачах. Разрешенные отдельным вызовом `dev-exec` коммиты реализации от этого не отменяются.

В созданном `backlog/config.yml` измени только `statuses` и `default_status`, сохранив остальные поля:

```yaml
statuses: [needs-info, ready-for-human, ready-for-agent, wontfix, resolved]
default_status: needs-info
```

В Backlog.md последний статус считается завершением, поэтому только `resolved` означает выполненную приемку и обязательные проверки; `wontfix` не выполняет blocker. Безопасный default не разрешает создание черновика: указывай статус каждой задачи явно, а `needs-info` используй только для явно разрешенного черновика. Готовность tracker по зависимостям сама по себе не разрешает исполнение: нужен `ready-for-agent`, а для каждого blocker - `resolved` и требуемый результат в выбранном worktree. Архивация не доказывает выполнение.

Не запускай этот setup поверх существующего backlog и не включай его молча: в 1.53.0 даже обычные команды чтения могут автоматически мигрировать старую конфигурацию и записи. Неясное или старое хранилище требует отдельного решения человека до команд tracker. Filesystem-only видит локальные файлы выбранного worktree, не объединяет живое состояние linked worktrees и не предотвращает коллизии IDs независимых clones.

## ПЕРЕД РАБОТОЙ

1. Определи точный абсолютный корень проекта и его выбранный worktree, а также принадлежащее ему хранилище. Убедись по локальным файлам, что конфигурация Backlog.md находится именно в этом корне: `backlog.config.yml` либо `backlog/config.yml`, `.backlog/config.yml` или соответствующий поддерживаемый `config.yaml`. Root config может задавать `backlog_directory`; проверь фактический каталог, включая symlinks. Если конфигураций несколько и выбор неясен, путь выходит за разрешенный проект или виден только tracker родительского каталога, остановись. Совпадение имени проекта или ID не доказывает принадлежность записи.
2. До обычных команд прочитай сам файл эффективной конфигурации без CLI. В `1.53.0` даже команды чтения запускают предварительную миграцию: она может переписать конфигурацию, создать milestones и переименовать drafts с изменением IDs. Не запускай их, если миграция возможна или ее отсутствие неясно. В частности, проверь актуальные `project_name`, `statuses`, `default_port`, `auto_open_browser`, `remote_operations`, `auto_commit`, `task_prefix` и отсутствие старого `milestones:`. При старой, поврежденной или непонятной схеме остановись и попроси человека отдельно решить вопрос миграции; не выполняй ее сам. `backlog --help` и `backlog --version` этого startup-шага не запускают.
3. Требуй заранее подготовленное локальное хранилище: `remote_operations: false`, `auto_commit: false`, `bypass_git_hooks: false`, `check_active_branches: false`; глобальный callback изменения статуса отсутствует или отключен. Перед изменением task проверь также отсутствие ее собственного `onStatusChange`. Не делай fetch/push, не включай callbacks, auto-commit, обход hooks или интеграцию с агентами. Инициализация может менять файлы инструкций и Git, а указатель не является согласием на нее или установку. Подробная подготовка - отдельное действие человека по [разделу выше](#подготовка-человеком), не выполняй setup сам. Разрешенные отдельным вызовом `dev-exec` commits реализации - не auto-commit tracker.
4. Только после этих проверок используй доступный CLI, права и настроенные статусы. Если инструкция, CLI, хранилище, нужная операция или данные недоступны, останови затронутую работу с точной причиной; не переключайся на `.scratch/`, другой tracker, MCP или прямую перезапись записей. Проверка версии и чтение конфигурации:

```bash
backlog --version
BACKLOG_CWD='<абсолютный корень проекта>' backlog config list
BACKLOG_CWD='<абсолютный корень проекта>' backlog config get statuses
```

Во всех примерах подставь реальные значения вместо `<...>`. Указывай `BACKLOG_CWD` для каждой команды: унаследованная переменная и текущий каталог могут указывать на другой проект, а CLI ищет конфигурацию и выше по дереву. Сверь результат с прочитанным файлом, выбранным корнем и каталогом. Если состояние нельзя надежно установить, остановись.

## СООТВЕТСТВИЕ ПОЛЕЙ И СТАТУСОВ

В native `status` задачи храни ровно одно из пяти значений nxs. Конфигурация должна содержать все пять разных значений, причем `resolved` - последний и единственный terminal status Backlog.md; иначе остановись и попроси человека подготовить конфигурацию. Не копируй ее как второй редактируемый список в task body и не меняй конфигурацию сам. При создании всегда явно передавай статус, не полагайся на default.

| Native status | Значение nxs |
| --- | --- |
| `ready-for-agent` | Работа согласована, предпосылки известны, исполнение агенту разрешено. |
| `needs-info` | Только явно разрешенный черновик с изолированным `[NEEDS CLARIFICATION: <вопрос>]`; не исполняется. Это native task, не Backlog draft. |
| `ready-for-human` | Нужно действие человека; в истории записаны причина, действие и ожидаемое доказательство. Не исполняется до возвращения в `ready-for-agent` и проверки результата. |
| `resolved` | Вся приемка и обязательные проверки действительно выполнены; повторно не исполняется. |
| `wontfix` | Пользователь отклонил или явно исключил работу; это не выполнение и не удовлетворение зависимости. Автоматически не переоткрывается. |

Неизвестный статус и существенное противоречие останавливают. `resolved` тоже не переоткрывай автоматически. Отдельное состояние архива не доказывает успех. Native `--ready`/`isReady` показывает лишь вычисление Backlog.md по видимым зависимостям и **не** дает разрешения агенту: при пустых зависимостях оно может быть истинным для `needs-info`, `ready-for-human` или `wontfix`. В `1.53.0` запись в `completed` может считаться завершенной независимо от ее status. Всегда проверяй настоящий статус и результат каждого blocker сам.

- Заголовок - native title. В `Description` сохраняй `**What to build:**`, цель, существенные решения, ограничения, конкретные source links и требования проверок; ticket должен быть понятен новой сессии без одного лишь перехода к spec. Согласованную ветку сохраняй там как `**Branch:** <точное имя>`; без согласованного выбора не выдумывай поле. Сохраняй там и явный `Do not commit`, если он задан, а также условия завершения.
- Acceptance Criteria - единственный редактируемый список критериев и отметок. Не создавай вторые checkboxes тех же критериев в `Description`. Definition of Done и требования проверок читай и сохраняй, если они есть.
- Native `dependencies` - единственный редактируемый список blockers: ID задачи указывает на задачу, от которой она зависит. Пустой список означает отсутствие blockers только после проверки источников, а не при неизвестности. Не добавляй в body независимо редактируемые `**Blocked by:**` или `**Status:**`. Не используй labels как второй статус.
- Source spec привязывай native `documentation` к фактическому пути созданного doc относительно корня проекта; также сохраняй ее doc ID для надежного повторного чтения. Другие источники и выбранные finding IDs указывай в `Description` или native `references`. Диагноз остается по своему локальному адресу. Не требуй parent task.
- История находится в native `Comments` внутри Markdown записи. Дописывай решения, согласование ветки, результаты проверок, фактические команды и commit IDs, не удаляя старое. Читай и сохраняй также ручные разделы, notes, plan и final summary. Если история старой записи находится в другом разделе и безопасно дописать в существующее место через CLI нельзя, остановись, не создавая конкурирующую историю.

## ЧТЕНИЕ И ПОИСК

Начиная с заранее распределенного точного ticket, прочитай его целиком, все comments, status, criteria, прямые и транзитивные dependencies, source docs и остальные указанные источники. Для повторного запроса и разбиения изучи существующие записи и их историю, в том числе `resolved`, `wontfix`, `completed` и архив; один заголовок или fuzzy search не доказывает идентичность. Используй точный полный ID с префиксом и сохраняй вместе с ним корень проекта, путь файла и ID/путь source doc. Ссылки на файлы сохраняй как реальные пути, полученные из выбранного проекта, а не предполагаемые имена.

```bash
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc list --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc search '<запрос>'
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc view '<doc-ID>' --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog task list --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog search '<запрос>' --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog task view '<task-ID>' --json
```

Списки и поиск - только навигация. Для каждой найденной записи прочитай весь соответствующий Markdown-файл из того же хранилища: JSON task содержит путь относительно корня; doc create выдает путь относительно корня, а doc search - относительно каталога docs. Doc list показывает ID и заголовки. Это необходимо также для ручных разделов и frontmatter, которые структурированный вывод может не показать. Например, после установления точного пути используй `cat '<абсолютный путь к записи>'`. Для полного обзора можно вывести файлы через `find '<абсолютный каталог backlog>' -type f -name '*.md' -print`; учти разрешенные symlinks и ошибки чтения, не считай неполный обход пустым результатом.

В `1.53.0` обычный список показывает локальные активные tasks; `task view` по точному ID также разрешает `completed`, но архив `archive/tasks` не входит в lookup/graph. Прочитай найденный архивный Markdown напрямую как часть того же локального хранилища, не копируя и не редактируя его. Если ID отсутствует, встречается более одного раза, запись недоступна или зависимость разрешается неоднозначно, остановись; не выбирай похожую запись. Не предполагай, что поиск показывает архив или всю историю. Не запускай архивирование, восстановление, удаление, cleanup или автоматический ремонт IDs ради чтения.

## ИНТЕРФЕЙС ДЛЯ ЧЕЛОВЕКА

В подготовленном проекте человек может открыть TUI доски, списка с поиском и фильтрами либо точной задачи. Действуют те же проверки конфигурации, статусов и полномочий:

```bash
BACKLOG_CWD='<абсолютный корень проекта>' backlog board
BACKLOG_CWD='<абсолютный корень проекта>' backlog task list
BACKLOG_CWD='<абсолютный корень проекта>' backlog task '<task-ID>'
```

В просмотре задачи `E` открывает ее в настроенном редакторе. После человеческого изменения агент заново читает тот же task через CLI и raw Markdown, включая comments и критерии; TUI не создает отдельное зеркало. Не считай нажатие в TUI проверкой приемки и не запускай интерфейс или skill автоматически.

## СОЗДАНИЕ И ОБНОВЛЕНИЕ

Запись разрешена только согласованным запросом и native permissions. Перед каждым изменением перечитай источник, точную цель и ее raw Markdown, проверь отсутствие конфликтующей конкурентной правки. Согласуй исключительный доступ с другими пишущими: повторное чтение не делает read-modify-write атомарным. Сохраняй чужой текст, поля, IDs, источники, отмеченные критерии и историю. Если CLI не может надежно сохранить существующие нестандартные поля/разделы или границы неоднозначны, остановись и попроси человека разрешить конфликт. Отказ безопасного обновления неоднозначного документа или секции не обходи ручной перезаписью или новым дубликатом.

До создания найди совпадения по полному корпусу docs и tasks, включая `completed` и архив, затем сверь содержание, источники и назначение. Один и тот же согласованный запрос повторно использует ту же запись и ID; идентичное состояние - no-op. При нескольких возможных совпадениях или неполном поиске не создавай новую запись. `resolved`/`wontfix` не переоткрывай автоматически; новый охват или конфликт с отклоненным решением сначала согласуй.

**Task spec.** CLI `1.53.0` создает doc без содержимого, поэтому создание и заполнение - два отдельных действия. Сохрани выданные ID и путь, перечитай созданную запись и только затем заполни согласованной spec:

```bash
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc create '<заголовок spec>' --type specification --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc view '<выданный doc-ID>' --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc update '<выданный doc-ID>' --content '<полный текст spec>'
BACKLOG_CWD='<абсолютный корень проекта>' backlog doc view '<выданный doc-ID>' --plain
```

Для существующего doc `--content` заменяет **весь** body: сначала прочитай текущий файл, составь полный результат с ручными дополнениями и незатронутым текстом, сверь отсутствие конкурирующего изменения. Не меняй title, path, tags или другие метаданные без необходимости. Проверь ID, фактический путь и полный текст после записи. Если после создания ответ потерян, найди созданную запись и установи ее однозначную принадлежность до заполнения; не создавай вторую.

**Ticket.** Создавай blockers раньше зависимых задач. Пример для согласованного готового ticket с одним существующим blocker и spec; если blocker отсутствует, убери `--dep`, а если источника spec нет, убери `--doc` и укажи фактические источники в `Description`. Добавляй повторные `--ac` и `--dep` для остальных критериев и blockers:

```bash
BACKLOG_CWD='<абсолютный корень проекта>' backlog task create '<заголовок>' \
  --description '<полное Description с целью, решениями, ограничениями, источниками и условиями завершения>' \
  --status ready-for-agent --doc '<путь к spec относительно корня проекта>' \
  --ac '<наблюдаемый критерий>' --dep '<полный ID blocker>' --plain
BACKLOG_CWD='<абсолютный корень проекта>' backlog task view '<выданный task-ID>' --json
```

При изменении существующей задачи выбирай точечные native операции и затем перечитывай JSON и raw файл. Например, после подтверждения результата конкретного критерия проверь его актуальный 1-based индекс; историю дописывай комментарием:

```bash
BACKLOG_CWD='<абсолютный корень проекта>' backlog task edit '<task-ID>' --check-ac '<индекс>'
BACKLOG_CWD='<абсолютный корень проекта>' backlog task edit '<task-ID>' --comment '<решение, проверка и результат>'
BACKLOG_CWD='<абсолютный корень проекта>' backlog task edit '<task-ID>' --status '<согласованный статус>'
```

`--ac` при edit добавляет критерий; не используй `--acceptance-criteria` или `--clear-ac` для замены списка и не снимай уже отмеченные критерии. В `1.53.0` edit `--dep` **заменяет весь** набор зависимостей, а `--doc` - всю документацию: перед необходимым изменением перечитай и передай полный новый набор с сохранением прежних элементов. Для ссылки можно применить `--add-ref`, не заменяя все references. `--description`, `--notes`, `--plan` и `--final-summary` заменяют соответствующий текст; не передавай только новую строку вместо старого содержимого. Для дополнения истории предпочитай `--comment`, для notes - `--append-notes`. Чтобы записать согласованный `Branch`, при необходимости обнови через `--description` полное текущее Description с добавленным полем, сохраняя весь остальной текст; при неясных границах остановись. Строка `---` отдельно в comment зарезервирована. Для многострочных значений передавай настоящие переводы строк и безопасно экранируй shell-спецсимволы, включая обратные кавычки; буквальное `\n` не превращается в перевод строки.

После **каждой** записи перечитай фактическую запись и проверь ID, содержимое, источники, blockers, status, отмеченные критерии и историю. При ошибке, неизвестном или частичном эффекте сначала прочитай фактическое состояние и выданные ID, включая возможный уже созданный пустой doc; повторяй только недостающее однозначно безопасное действие. Не повторяй создание, append, изменение статуса или другую операцию вслепую.

## ИСПОЛНЕНИЕ И ПЕРЕДАЧА

Исполняй только точный назначенный `ready-for-agent` ticket. До продуктовых правок для каждого blocker прочитай реальную запись и ее историю, установи однозначный `resolved` и проверь нужный результат в выбранном worktree. Отмененный, отсутствующий, неоднозначный или непроверяемый blocker - остановка. Если blocker в архиве и native dependency graph его не разрешает, не объявляй зависимость выполненной по расположению; остановись для решения человека. При смене ветки/worktree перечитай ticket и повторно проверь результат blockers в фактическом дереве: статус на другой ветке, ancestry и cross-branch просмотр не доказывают наличие результата здесь.

`Do not commit` несовместим с вызовом `dev-exec`: остановись до реализации и попроси изменить запрет, не меняя его самостоятельно. Сохрани согласованную ветку и решение в ticket до реализации; при неизвестном эффекте перечитай запись. `ready-for-human` требует записать причину, действие и ожидаемое доказательство. `resolved` ставь только после всех наблюдаемых критериев и обязательных проверок, записи реальных результатов и разрешенных commit IDs в историю. Не закрывай parent, не выбирай следующий ticket и не запускай другой skill автоматически.

CLI/TUI читают локальное состояние выбранного checkout и доступный `completed`; linked worktrees не являются единым общим состоянием. Вне разрешенного worktree не ищи результат как замену локальной проверке. У upstream есть отдельные улучшения выделения IDs для [linked worktrees](https://github.com/MrLesk/Backlog.md/pull/710), но они не доказывают общую область видимости или atomic claim; последовательные IDs могут конфликтовать между [независимыми clones](https://github.com/MrLesk/Backlog.md/issues/711). Профиль не обещает защиту от коллизий, атомарный захват или конкурентную идемпотентность. При конфликте остановись без перенумерации.

Передай точные project/root, ID и пути созданных или повторно использованных записей, реальные blockers, записанные изменения, ограничения и причину любой остановки. Не выдавай описание команд или исходники upstream за выполненную проверку.

## ПРОВЕРЕННАЯ ОБЛАСТЬ

На одноразовых локальных проектах с Backlog.md `1.53.0` и Codex CLI `0.166.0` выполнены отдельные явные source-вызовы `to-spec`, `to-tickets` и `dev-exec`: docs, tasks, source links, native dependencies, comments, критерии, согласованная ветка, реальные Python-проверки, атомарные commits и запись их IDs до `resolved`. Повторные вызовы подготовки новой сессией сохранили те же IDs и весь Markdown побайтно, включая ручные дополнения.

В реальном TUI через agterm `0.40.0` проверены список, поиск, status filter, подробности и `E` с `/usr/bin/nano`. Изменение native comment сохранено через редактор из TUI, затем прочитано через CLI из той же записи.

Проверены пять статусов и отрицательные условия исполнения: неизвестный status, архив, отклоненный/отсутствующий/неоднозначный blocker, отсутствие результата `resolved` blocker и `Do not commit`. Уже `resolved` не исполнялся повторно; следующий ticket не запускался, родитель выполненного child остался открытым. Проверены оба local defaults и остановки без fallback при отсутствующей инструкции, недоступном CLI и безопасном отказе обновления неоднозначного doc; исходные документы сохранились.

Обычный Codex `workspace-write` в smoke запретил Git metadata writes: исполнение остановилось в `ready-for-human`. Только после отдельного разрешения пользователя одноразовый native profile расширил доступ к `.git` выбранного fixture, оставив command network выключенной и `.git/config` read-only; повторный явный вызов завершил проверку и commit. Это не разрешение автоматически расширять permissions. Native sandbox применялся; command-environment ограничение missing-CLI probe и запреты действий в prompts не являются дополнительным host sandbox.

Для `rnd-debug` и `dev-review` проверено только чтение docs/comments/blockers по общему tracker contract, без запуска полной диагностики или review. Проверка source skills не доказывает native регистрацию, непрерывный multi-turn resume, все клиенты/версии, remote API, MCP, Web UI, миграцию старых хранилищ или корректность linked worktrees и независимых concurrent clones. Рабочие проекты, пользовательские установки и settings не настраивались; `.scratch` default не менялся.
