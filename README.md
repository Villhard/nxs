# nxs

Девять самостоятельных skills для основного flow разработки с coding agents. Инструкции задают цель и этапы; способ выполнения выбирает модель.

## Установка и обновление

```bash
npx skills@latest add -g Villhard/nxs
```

В меню выбираются skills и клиент. Устанавливается опубликованная версия. Обновление выбранного skill:

```bash
npx skills@latest update -g dev-exec
```

Источник и предлагаемый diff показывают, какая установка изменится. Локальная разработка описана в [CONTRIBUTING](CONTRIBUTING.md#local-development-and-release).

## Порядок работы

Обсуждение → task spec при необходимости → tickets → исполнение и приемка каждого ticket. Диагностика дает дополнительный вход в подготовку; commit доступен отдельно. Skills вызываются независимо, синтаксис `/` или `@` зависит от клиента.

Task records (`spec.md`, `branch.md`, `issues/<NN>-<slug>.md`) хранятся одним комплектом вне удаляемых ticket worktrees: по умолчанию `<основное рабочее дерево Git>/.scratch/<feature-slug>/`. Согласованное место и существующие records имеют приоритет; автоматической миграции нет. Backlog находится в `.scratch/backlog/<slug>.md`, `root-cause.md` - в каталоге records. Отчеты и доказательства сразу сохраняются в `artifacts/` рядом с records либо в выбранном постоянном месте со ссылкой из ticket.

1. [to-spec](skills/to-spec/SKILL.md) и [to-tickets](skills/to-tickets/SKILL.md) подготавливают задачу и самостоятельные результаты; [dev-exec](skills/dev-exec/SKILL.md) выполняет ticket в отдельной ветке/worktree, проводит достаточные авторские проверки и переводит его в `agent-review`.
2. Отдельный [dev-review](skills/dev-review/SKILL.md) поручает проверку двум независимым read-only reviewer с фокусами на реализацию и на требования/документацию. При полном охвате и отсутствии блокирующих замечаний ticket переходит в `human-review`; явный `dev-review skip` тоже переводит его туда, но не считается успешной проверкой.
3. Человек дает `reject` с замечаниями или `approve` показанного ticket и ревизии. Согласованные исправления требуют нового review и решения.
4. Approve разрешает доставку в `Spec branch` для `feature` или `Target branch` для `direct` и безопасную очистку. `resolved` возможен после подтверждения доставки и выполнения AC и DoD.

Неизвестные и чужие данные сохраняются; даже обычный `git worktree remove` удаляет ignored-файлы. При риске очистка откладывается с причиной и следующим шагом, не отменяя `resolved`. После одиночного поручения следующий ticket не начинается автоматически; очередь ожидает отдельного review или skip и решения человека, проверяя зависимости перед продолжением.

Review всей feature и [sync-spec](skills/sync-spec/SKILL.md) вызываются отдельно. Перед отдельно порученной подготовкой MR/PR feature нужна актуальная успешная сверка либо явный skip, о котором сообщается; изменения реализации, включая незакоммиченные, делают прежнее решение неактуальным. Это не запускает автоматически публикацию или merge; для `direct` без feature-ветки отдельный gate не придуман. Подробнее: [контракты](SPEC.md#контракты) и [CONTRIBUTING](CONTRIBUTING.md). Проверки исходников не доказывают совместимость всех клиентов.
