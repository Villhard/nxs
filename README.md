# nxs

Восемь самостоятельных skills для обсуждения, подготовки и выполнения задач coding agents.

## Установка

```bash
npx skills@latest add -g Villhard/nxs
```

Выбери skills и клиента в меню. Устанавливается опубликованная версия; локальный candidate - по [CONTRIBUTING](CONTRIBUTING.md#локальная-разработка-и-публикация).

## Какой скилл выбрать

| Скилл | Назначение |
| --- | --- |
| [rnd-grill](skills/rnd-grill/SKILL.md) | Обсудить решение без записи. |
| [to-spec](skills/to-spec/SKILL.md) | Сохранить согласованную спеку задачи. |
| [to-tickets](skills/to-tickets/SKILL.md) | Подготовить самодостаточные проверяемые tickets. |
| [dev-exec](skills/dev-exec/SKILL.md) | Выполнить один ticket с проверками и коммитами. |
| [dev-review](skills/dev-review/SKILL.md) | Независимые Standards/Spec reviewers, без правок. |
| [rnd-debug](skills/rnd-debug/SKILL.md) | Подтвердить причину сбоя без исправления кода. |
| [sync-spec](skills/sync-spec/SKILL.md) | Обновить проектную спецификацию по реализованному. |
| [dev-commit](skills/dev-commit/SKILL.md) | Закоммитить выбранные существующие правки. |

## Порядок работы

```text
/rnd-grill Как лучше ограничить число запросов к API?
/to-spec Сохрани согласованное в .scratch/rate-limit/spec.md
/to-tickets .scratch/rate-limit/spec.md
/dev-exec .scratch/rate-limit/issues/01-limit.md
```

Синтаксис `/` или `@` зависит от клиента. Вызовы явные; `dev-commit` также принимает прямую просьбу закоммитить. Для бага начни с `rnd-debug`; малой согласованной задаче достаточно `to-tickets`. `dev-review` и `sync-spec` вызываются отдельно: автоматической цепочки нет.

`dev-exec` коммитит проверенные шаги. Неизвестный выбор ветки согласуется до реализации и сохраняется в ticket. `Do not commit` останавливает исполнение; автоматического push нет.

## Где хранятся записи

Без настройки tracker используются `.scratch/<feature-slug>/spec.md` и `.scratch/<feature-slug>/issues/<NN>-<slug>.md`. Спека задачи хранит намерение; проектная SPEC - реализованное. Для обычной работы не требуется предварительная настройка или секция `## nxs`.

Чтобы использовать другой tracker, подготовь Markdown-инструкцию о его реальном хранилище spec и tickets и доступных операциях. В ней опиши, как читать записи целиком, включая body, comments, зависимости и статусы; создавать и обновлять spec и tickets; работать с зависимостями и статусами; проверять фактический результат операций. Можно попросить агента подготовить такую инструкцию обычной просьбой.

Добавь необязательный pointer в уже применимые project instructions, в секцию `## nxs`:

```markdown
## nxs
Трекер: docs/tracker.md
```

Pointer также может находиться в применимых global instructions; project pointer имеет приоритет над global. Относительный путь разрешается от файла instructions, содержащего pointer, а `~` - от домашнего каталога пользователя. Загрузка instructions находится вне ответственности skills. Pointer не предоставляет доступ к tracker и не устанавливает инструменты: нужные доступы и операции должны быть доступны отдельно.

Явный путь или URL обозначает конкретную запись и сам по себе не переключает backend: необходимо установить принадлежность записи и использовать соответствующую согласованную инструкцию, при неоднозначности - уточнить. Если настроенная инструкция отсутствует или недоступна либо недоступна необходимая операция, затронутая работа останавливается с причиной, без fallback в `.scratch` или создания второго набора записей. После неизвестного результата записи сначала прочитай ее фактический эффект и IDs, прежде чем повторять операцию.

Явный вызов `to-spec` или `to-tickets` с согласованным remote назначением разрешает соответствующую публикацию; вызов `dev-exec` для remote ticket - необходимые обновления этого ticket в согласованном проекте. Другие файлы не публикуются, parent не закрывается и копии не синхронизируются без запроса.

### Необязательный профиль Backlog.md

[Профиль Backlog.md](trackers/backlog.md) - самостоятельная tracker instruction для отдельного локального backlog проекта. После явного подключения новые task specs хранятся в Backlog.md docs, а tickets - в задачах со ссылками на эти документы. Проектные `SPEC.md`/`.SPEC.md` остаются на своих местах, диагнозы и evidence `rnd-debug` - локально. Не переноси секреты и частные инструкции в backlog. Чтение README или установка nxs ничего не настраивает и не мигрирует.

Для подготовки нужен отдельно доступный Backlog.md; CLI рекомендуется для агентов, человеку достаточно TUI, MCP и Web UI не обязательны. Установка инструмента - отдельное решение пользователя.

Пример для Backlog.md 1.53.0: только в корне нового или одноразового проекта, изменения которого явно разрешены, и только если там и в родительских каталогах нет существующего backlog. Сначала сохрани чужие файлы и убедись, что выбранные `backlog/`, `.backlog/` и `backlog.config.yml` не заняты. Затем:

```bash
env -u BACKLOG_CWD backlog init "My Project" \
  --defaults --no-git --integration-mode none \
  --check-branches false --include-remote false \
  --bypass-git-hooks false --auto-open-browser false \
  --backlog-dir backlog --config-location folder
```

Init создает `backlog/` и `backlog/config.yml`. Флаги выбирают filesystem-only без Git-интеграции tracker и без клиентских инструкций; обычный init может записывать инструкции и выполнять Git-действия. Не добавляй к `--integration-mode none` флаги `--agent-instructions` или `--install-claude-agent`: версия 1.53.0 не принимает это сочетание. Не включай tracker auto-commit, bypass hooks, remote operations или callbacks смены статуса, в том числе на отдельных задачах. Разрешенные отдельным вызовом `dev-exec` коммиты реализации от этого не отменяются.

В созданном `backlog/config.yml` измени только `statuses` и `default_status`, сохранив остальные поля:

```yaml
statuses: [needs-info, ready-for-human, ready-for-agent, wontfix, resolved]
default_status: needs-info
```

В Backlog.md последний статус считается завершением, поэтому только `resolved` означает выполненную приемку и обязательные проверки; `wontfix` не выполняет blocker. Безопасный default не разрешает создание черновика: указывай статус каждой задачи явно, а `needs-info` используй только для явно разрешенного черновика. Готовность tracker по зависимостям сама по себе не разрешает исполнение: нужен `ready-for-agent`, а для каждого blocker - `resolved` и требуемый результат в выбранном worktree. Архивация не доказывает выполнение.

Не запускай этот setup поверх существующего backlog и не включай его молча: в 1.53.0 даже обычные команды чтения могут автоматически мигрировать старую конфигурацию и записи. Неясное или старое хранилище требует отдельного решения человека до команд tracker. Filesystem-only видит локальные файлы выбранного worktree, не объединяет живое состояние linked worktrees и не предотвращает коллизии IDs независимых clones.

Скопируй [профиль](trackers/backlog.md) в `docs/tracker.md` своего проекта, затем добавь в применимые project instructions pointer из примера выше. Например, из корня проекта, если исходный checkout уже доступен:

```bash
mkdir -p docs
cp -n /path/to/nxs/trackers/backlog.md docs/tracker.md
```

Если файл уже занят, выбери другой свободный путь и укажи его в pointer, не перезаписывая чужую инструкцию. Профиль можно скопировать и без checkout; установленным skills не нужны checkout nxs или другой skill. Дальнейшие операции и остановки описаны в самой копии профиля.

Профиль проверен с Backlog.md `1.53.0`, Codex CLI `0.166.0` и реальным TUI на disposable fixtures, включая отдельные source-вызовы `to-spec`, `to-tickets`, `dev-exec`. Точный охват и ограничения - в [профиле](trackers/backlog.md#проверенная-область); это не заявление native регистрации или совместимости всех клиентов и версий. Справочные источники: [CLI](https://github.com/MrLesk/Backlog.md/blob/v1.53.0/CLI-INSTRUCTIONS.md) и [конфигурация](https://github.com/MrLesk/Backlog.md/blob/v1.53.0/ADVANCED-CONFIG.md).

## Обновление

```bash
npx skills@latest update -g dev-exec
```

Проверь source и весь предлагаемый diff: фильтр имени не ограничивает источник. Не подтверждай незапланированное удаление или замену чужого skill.

Файлы и установка не доказывают совместимость клиента. [SPEC](SPEC.md) - контракты и ограничения; [CONTRIBUTING](CONTRIBUTING.md) - изменение и проверки.
