# nxs

Девять самостоятельных skills для coding agents: обсудить решение, сохранить спеку задачи и tickets, выполнить один ticket проверенными шагами с коммитами. Review и обновление проектных specs вызываются отдельно.

## Установка

```bash
npx skills@latest add -g Villhard/nxs
```

Выбери нужные skills и клиента в меню. Команда устанавливает опубликованную версию, не локальные правки. Для candidate см. [CONTRIBUTING](CONTRIBUTING.md#локальная-разработка-и-публикация).

## Какой скилл выбрать

| Скилл | Когда нужен |
| --- | --- |
| [rnd-grill](skills/rnd-grill/SKILL.md) | Разобрать неопределенность и согласовать решение в разговоре. Ничего не записывает. |
| [to-spec](skills/to-spec/SKILL.md) | Сохранить согласованное решение, причины и приемку в спеку задачи. Не новое интервью. |
| [to-tickets](skills/to-tickets/SKILL.md) | Разбить спеку на самодостаточные проверяемые tickets с реальными blockers. Малой задаче достаточно одного. |
| [dev-exec](skills/dev-exec/SKILL.md) | Выполнить один готовый ticket: законченный шаг, проверка поведения, атомарный коммит, следующий шаг. |
| [dev-review](skills/dev-review/SKILL.md) | Два независимых reviewers: Standards и Spec. Включает выбранные committed, staged, unstaged и untracked изменения; код не правит. |
| [rnd-debug](skills/rnd-debug/SKILL.md) | Воспроизвести сбой, различить гипотезы и сохранить подтвержденную причину. Код не исправляет. |
| [sync-spec](skills/sync-spec/SKILL.md) | Обновить живые проектные `SPEC.md` или частные `.SPEC.md` по реализованному. Без существенного изменения - no-op. |
| [dev-commit](skills/dev-commit/SKILL.md) | Закоммитить существующие разрешенные правки, сохранив чужой index и рабочие файлы. |
| [nxs-setup](skills/nxs-setup/SKILL.md) | Настроить инструкции проекта, хранение или формат коммитов точным одобренным diff; либо только сообщить готовность. |

Используй синтаксис клиента: `/dev-exec` или `@dev-exec`, если поддерживается. Все skills требуют явного выбора; `dev-commit` также принимает прямую просьбу закоммитить. Файлы skill сами по себе не доказывают регистрацию или совместимость клиента.

## Порядок работы

- Идея: `rnd-grill` → `to-spec` → `to-tickets` → `dev-exec <ticket>`.
- Баг: `rnd-debug` → при необходимости `to-spec` → `to-tickets` → `dev-exec <ticket>`.
- Выбранные доказанные замечания `dev-review` → `to-spec`/`to-tickets`, не напрямую исполнителю.
- После реализации отдельно выбираются `dev-review` и `sync-spec`. `nxs-setup` вне цепочки; `dev-commit` доступен самостоятельно.

Это возможные переходы, не автоматическая цепочка. Для небольшой согласованной задачи `to-tickets` принимает разговор, подтвержденный диагноз или выбранные замечания без обязательного промежуточного файла. Обычная работа агента вне `dev-exec` не запрещена; сам `dev-exec` принимает только ticket.

```text
/rnd-grill Как лучше ограничить число запросов к API?
/to-spec Сохрани согласованное в .scratch/rate-limit/spec.md
/to-tickets .scratch/rate-limit/spec.md
/dev-exec .scratch/rate-limit/issues/01-limit.md
/dev-review Проверь весь ticket от его исходного HEAD, включая рабочее дерево
/sync-spec .scratch/rate-limit
/rnd-debug При повторной оплате создаются два заказа
/dev-commit Только изменения поиска
/nxs-setup project
/nxs-setup project --readiness
```

Вызов `dev-exec` разрешает реализацию ticket и коммиты законченных проверенных шагов без повторного approve каждого шага. TDD ситуативен; воспроизведение бага и проверка исправления обязательны, где применимы. `Do not commit` конфликтует с этим контрактом и останавливает исполнение до согласованного изменения запрета. Ticket закрывается только после всей приемки и обязательных проверок проекта. Ни review, ни sync-spec, ни push автоматически не запускаются.

## Где хранятся записи

Без setup: `.scratch/<feature>/spec.md` и `.scratch/<feature>/issues/<NN>-<slug>.md`. Спека задачи хранит намерение и причины решений; проектные `SPEC.md`/`.SPEC.md` описывают реализованное и обновляются через `sync-spec`. Отдельной системы ADR и автоматической записи glossary нет; существующие документы читаются без миграции.

`nxs-setup` может добавить в `## nxs` строку `Трекер: <путь к Markdown-инструкции>.` Project instruction важнее global. Инструкция описывает реальное хранилище и доступные операции CLI/MCP/API; это не runtime или набор готовых интеграций. Если настроенный документ или инструмент недоступен, операция останавливается, а не создает дубликат в `.scratch`. Указание пути/URL конкретной записи не переключает backend молча.

Публикация в согласованную remote цель разрешается вызовом соответствующего writer; обновление исполняемого remote ticket - вызовом `dev-exec`. Это не разрешает закрывать parent или публиковать постороннее. Неизвестный эффект сначала проверяется чтением. Возможность настройки не означает проверенную совместимость с внешним сервисом.

## Обновление и настройка

Пример обновления: `npx skills@latest update -g dev-exec`. Проверь пути, источник и предлагаемые изменения: фильтр имени не фильтрует источник, меню может предложить удалить другие записи того же source/ref. Не подтверждай незапланированное удаление или замену одноименного чужого skill.

Правки исходников не меняют установленные копии, пользовательские tickets, Git settings и внешние сервисы. `nxs-setup` не устанавливает tools или skills и применяет только показанный одобренный diff; отказ и актуальная настройка ничего не записывают. Readiness касается только нужных операций, не требует reviewers для планирования.

Source discovery и установка не доказывают live invocation. Наблюденные проверки и ограничения - в [SPEC](SPEC.md). Другие клиенты и remote backends остаются непроверенными без отдельного запуска.
