# nxs

Девять самостоятельных skills для основного flow разработки с coding agents. Инструкции задают цель и этапы; способ выполнения выбирает модель.

## Установка и обновление

```bash
npx skills@latest add -g Villhard/nxs
```

В меню выбираются skills и клиент. Устанавливается опубликованная версия. Обновление выбранного skill:

```bash
npx skills@latest update -g dev-exec
```

Источник и предлагаемый diff показывают, какая установка изменится. Локальная разработка описана в [CONTRIBUTING](CONTRIBUTING.md#local-development-and-release).

## Порядок работы

Обсуждение → task spec при необходимости → tickets → исполнение и приемка каждого ticket. Диагностика дает дополнительный вход в подготовку; commit доступен отдельно. Skills вызываются независимо, синтаксис `/` или `@` зависит от клиента.

Task records (`spec.md`, `branch.md`, `issues/<NN>-<slug>.md`) лежат одним комплектом вне удаляемых ticket worktrees: по умолчанию `<основное рабочее дерево Git>/.scratch/<feature-slug>/`. Значения backlog и `root-cause.md` прежние - `.scratch/backlog/<slug>.md` и `root-cause.md` в каталоге records. Выбор одинаков из основного и linked worktree; явное место и существующие records приоритетнее. Одноименная копия `.scratch` внутри worktree не авторитетна: пути к records и к реализации разрешаются независимо, поэтому смена каталога и устаревшая копия не меняют место записи. Предварительная настройка не требуется.

Отчеты, вложения и доказательства сохраняются сразу рядом с исходными records - по умолчанию в `artifacts/` каталога records - либо в явно выбранном постоянном месте со ссылкой из ticket: временный путь не остается единственным источником. Существующие записи не перезаписываются, одинаковые имена разбираются по содержимому без потери данных, время изменения не доказывает актуальность. Доказательство считается сохраненным, только если нужные вложения открываются по ссылкам из самого сохраненного отчета, в том числе после вынужденного переименования. Выбранные и tracked records не переносятся и не коммитятся автоматически ради нового default; код и project specs по-прежнему доставляет Git.

При затруднении агент сохраняет данные и сообщает препятствие со следующим шагом. Общий `branch.md` и task spec обновляются несколькими tickets: перед записью актуальная версия перечитывается, результаты других tickets и ручные дополнения сохраняются.

Если общая task spec есть, исполнитель записывает в ней проверенный результат каждого ticket со ссылкой на ticket и доказательства, а не только отмечает checkbox. Для этого не требуется создавать spec или новый обязательный раздел.

Жизненный цикл ticket:

1. `dev-exec` выполняет работу в отдельной ветке/worktree, проверяет результат и переводит `in-progress` в `agent-review`.
2. Отдельный вызов `dev-review` запускает независимого проверяющего, который не исправляет код. Проверяющий получает исходные требования по их собственным путям и проверяемый результат по его ревизии; применимые project specs берутся из проверяемого состояния, а не из старого `main`. Отчет сохраняет вызывающий агент в исходный ticket. При известном охвате и отсутствии блокирующих замечаний ticket переходит в `human-review`. Явный `dev-review skip` также переводит ticket в `human-review`, но записывается как пропуск, а не успешная проверка.
3. В `human-review` пользователь дает `reject` с проблемами или `approve` показанного результата; решение должно однозначно относиться к ticket и его ревизии. Замечания можно обсудить; согласованные исправления возвращают ticket в `in-progress` и требуют нового review. Агентский approval не заменяет человеческий.
4. Человеческий `approve` разрешает интеграцию и безопасную очистку без отдельного запроса merge. Результат доставляется в `Spec branch` для `feature` или `Target branch` для `direct`; `resolved` возможен только после подтвержденной доставки и выполнения AC и DoD.

При очистке агент выходит из worktree и проверяет недоставленную историю, изменения, untracked/ignored-файлы и доступность records вне удаляемого места. Нужный отчет или вложение, уже созданное внутри worktree, переносится в постоянное место в составе этой очистки: ссылки обновляются, содержимое сверяется, и только затем удаляются временные копии. Успешно сохраненный отчет не разрешает удалять прочие данные; неизвестные файлы и чужая работа остаются на месте без автоматического переноса или бэкапа до явного решения. Approve и новый default не выбирают маршрут миграции для существующих выбранных или tracked records - без согласованного маршрута worktree удерживается. Обычный `git worktree remove` без `--force` тоже удаляет ignored-файлы: untracked, ignored данные и принадлежность проверяются до первого удаления, а не пробным удалением с восстановлением. force и сплошное архивирование не применяются. Рабочие ветка и worktree удаляются только при подтвержденной безопасности; при риске очистка откладывается с причиной и следующим шагом, не отменяя `resolved`.

После одиночного поручения следующий ticket не начинается автоматически. В порученной очереди агент ожидает отдельного review или skip и человеческого решения; для следующего доступного ticket проверяет реальные зависимости и доступность их результатов, затем создает свое место от актуальной базы.

Review всей feature вызывается отдельно и не заменяет approval ticket. `sync-spec` также вызывается отдельно и не требуется для `resolved` отдельного ticket; закрытие очереди не запускает review feature, sync или публикацию MR/PR.

Перед отдельно порученной подготовкой MR/PR всей feature нужен актуальный успешный `sync-spec` либо явный `sync-spec skip`. В общем `branch.md` хранится исходное `synced: false`, а после сверки - `synced: true`, результат, совокупный охват, ревизия и пояснение. Подтвержденное отсутствие необходимых правок project specs тоже является успехом; ошибка или недостаток доказательств - нет. Skip не запускает сверку и сохраняет `synced: false` с отдельным фактом пропуска для текущей ревизии. При предложении MR/PR после skip агент прямо сообщает о пропущенной синхронизации.

Task spec для этого не требуется и не дублирует состояние. Новые изменения реализации, включая незакоммиченные, делают прежние sync и skip неактуальными: `synced` возвращается в `false`, история сохраняется, нужен новый sync либо явный skip. Без актуального решения подготовка MR/PR не допускается. Успех и skip не запускают подготовку, публикацию, review или финальный merge и не заменяют соответствующие поручения. Маршрут совокупного sync перед MR/PR в `direct` без feature-ветки остается несогласованным; эти правила не подменяют его.

[SPEC](SPEC.md) описывает контракты; [CONTRIBUTING](CONTRIBUTING.md) - структуру и проверки. Проверки исходников сами по себе не доказывают совместимость всех клиентов.
