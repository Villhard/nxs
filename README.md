# nxs

Девять самостоятельных skills для основного flow разработки с coding agents. Инструкции задают цель и этапы; способ выполнения выбирает модель.

## Установка и обновление

```bash
npx skills@latest add -g Villhard/nxs
```

В меню выбираются skills и клиент. Устанавливается опубликованная версия. Обновление выбранного skill:

```bash
npx skills@latest update -g dev-exec
```

Источник и предлагаемый diff показывают, какая установка изменится. Локальная разработка описана в [CONTRIBUTING](CONTRIBUTING.md#local-development-and-release).

## Порядок работы

Обсуждение → task spec при необходимости → tickets → исполнение и приемка каждого ticket. Диагностика дает дополнительный вход в подготовку; commit доступен отдельно. Skills вызываются независимо, синтаксис `/` или `@` зависит от клиента.

Жизненный цикл ticket:

1. `dev-exec` выполняет работу в отдельной ветке/worktree, проверяет результат и переводит `in-progress` в `agent-review`.
2. Отдельный вызов `dev-review` запускает независимого проверяющего, который не исправляет код. При известном охвате и отсутствии блокирующих замечаний ticket переходит в `human-review`. Явный `dev-review skip` также переводит ticket в `human-review`, но записывается как пропуск, а не успешная проверка.
3. В `human-review` пользователь дает `reject` с проблемами или `approve` показанного результата; решение должно однозначно относиться к ticket и его ревизии. Замечания можно обсудить; согласованные исправления возвращают ticket в `in-progress` и требуют нового review. Агентский approval не заменяет человеческий.
4. Человеческий `approve` разрешает интеграцию и безопасную очистку без отдельного запроса merge. Результат доставляется в `Spec branch` для `feature` или `Target branch` для `direct`; `resolved` возможен только после подтвержденной доставки и выполнения AC и DoD.

При очистке агент выходит из worktree и проверяет недоставленную историю, изменения, untracked/ignored-файлы и доступность records вне удаляемого места. Рабочие ветка и worktree удаляются только при подтвержденной безопасности; при риске очистка откладывается с причиной и следующим шагом, не отменяя `resolved`.

После одиночного поручения следующий ticket не начинается автоматически. В порученной очереди агент ожидает отдельного review или skip и человеческого решения; для следующего доступного ticket проверяет реальные зависимости и доступность их результатов, затем создает свое место от актуальной базы.

Review всей feature вызывается отдельно и не заменяет approval ticket. `sync-spec` также вызывается отдельно и не требуется для `resolved` отдельного ticket; закрытие очереди не запускает review feature, sync или публикацию MR/PR.

По умолчанию records лежат в `.scratch/<feature-slug>/`: `spec.md`, `branch.md`, `issues/<NN>-<slug>.md`, `root-cause.md`. Предварительная настройка не требуется.

[SPEC](SPEC.md) описывает контракты; [CONTRIBUTING](CONTRIBUTING.md) - структуру и проверки. Проверки исходников сами по себе не доказывают совместимость всех клиентов.
